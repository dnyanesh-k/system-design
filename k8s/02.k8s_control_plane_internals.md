# 1. The control plane: the brain of a Kubernetes cluster

The Kubernetes control plane is the collection of components responsible for managing the cluster's desired state and coordinating changes to its resources.

A Kubernetes cluster contains two broad categories of responsibilities:

- Control plane: accepts API requests, stores cluster state, makes scheduling decisions, and runs control loops that coordinate the cluster.
- Worker nodes: provide the compute environment where application Pods run.

The control plane does not usually execute your application containers itself. Instead, it records what should run, determines where workloads should run, and coordinates the components that make those workloads run.

## 1.1 Control-plane architecture

## Control plane

kube-apiserver

Central API entry point

etcd

Persistent cluster state

kube-scheduler

Pod placement decisions

kube-controller-manager

Built-in reconciliation loops

cloud-controller-manager

Cloud integration, when deployed

API requests, resource watches, scheduling decisions and status updates

## Worker node

kubelet

Ensures assigned Pods are running as specified

Container runtime

Creates and manages containers

Pods and application containers

This is a logical architecture, not a mandatory physical layout. In a managed service such as Amazon EKS, AWS operates much of the control-plane infrastructure, while you manage workloads and worker compute according to your chosen EKS configuration.

A key principle is that the API server is the central communication interface, but it is not the component that performs every cluster operation. The scheduler, controllers, kubelets, and other components perform their respective responsibilities by communicating through the Kubernetes API.

## 1.2 Responsibilities of the main components

| Component                  | Primary responsibility                                            | Example                                                      |
| -------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------ |
| `kube-apiserver`           | Exposes and processes the Kubernetes API                          | Accepts a Deployment update                                  |
| `etcd`                     | Persists Kubernetes API state                                     | Stores the accepted resource state                           |
| `kube-scheduler`           | Selects nodes for unscheduled Pods                                | Assigns a Pod to a suitable worker                           |
| `kube-controller-manager`  | Runs built-in controllers                                         | Ensures a Deployment's replica hierarchy converges           |
| `cloud-controller-manager` | Integrates Kubernetes with cloud provider functionality when used | Coordinates cloud load balancers or node-related cloud state |
| `kubelet`                  | Reconciles Pods assigned to its node                              | Requests containers to be started through the runtime        |
| Container runtime          | Manages container execution                                       | Starts a container using containerd and the CRI interface    |

These components have distinct responsibilities, but they are not independent in the sense of having unrelated state. They cooperate around API objects and their desired and observed states.

# 2. The kube-apiserver request pipeline

The `kube-apiserver` is the primary interface through which Kubernetes API objects are created, read, modified, and deleted.

When you execute:

```
kubectl apply -f deployment.yaml
```

`kubectl` does not directly create a container on a worker node. It sends an API request to the Kubernetes API server.

The request must pass through several processing stages before a change can be persisted.

## 2.1 End-to-end request flow

### 1

1\. Client request

kubectl constructs an API request from the manifest

### 2

2\. Authentication

The API server identifies the caller

### 3

3\. Authorization

The server checks whether the caller may perform the requested action

### 4

4\. Admission

Applicable admission mechanisms inspect or modify the request

### 5

5\. Validation and processing

The resource and requested changes are checked

### 6

6\. Persistence

The API server stores the accepted state through its storage layer

### 7

7\. Response

The API server returns a response to the client

This diagram is a conceptual sequence. The exact internal processing path depends on the operation, enabled API features, resource type, and admission configuration. Do not treat it as a complete implementation-level call graph.

## 2.2 Authentication: who are you?

Authentication establishes the identity associated with an API request.

Depending on the cluster configuration, identity can be established using mechanisms such as client certificates, bearer tokens, or an external identity provider.

For example, in an EKS environment, IAM authentication can be used to establish a Kubernetes identity for a caller. The exact mapping and access setup depend on the cluster's authentication configuration.

Suppose a user executes:

```
kubectl get pods -n production
```

The API server must establish who the caller is before evaluating the request under the applicable access-control mechanisms.

Authentication answers:

> Who is making this request?

It does not, by itself, establish whether the caller is allowed to read Pods in the `production` namespace.

An unauthenticated request can be rejected before authorization is reached.

## 2.3 Authorization: what are you allowed to do?

Authorization determines whether the authenticated identity may perform the requested operation on the requested resource.

Kubernetes commonly uses Role-Based Access Control (RBAC). RBAC policies grant permissions through Roles or ClusterRoles and associate them with identities through RoleBindings or ClusterRoleBindings.

Consider this request:

```
kubectl delete pod payments-api-7d8f9c9d7b-x2abc \
  -n production
```

The API server evaluates whether the caller has permission to delete a Pod in that namespace.

A user may have permission to:

- List Pods in `development`.
- Read Deployments in `production`.
- Be denied permission to delete Pods in `production`.

Permissions are evaluated in the context of the requested API operation, resource, namespace, and applicable authorization rules.

Important distinction: Authentication identifies the caller; authorization evaluates the caller's permissions.

## 2.4 Admission control: should this request be admitted?

Admission control runs after authentication and authorization for applicable write requests. Admission mechanisms can reject requests or modify them before persistence.

There are two important categories.

Mutating admission can modify an incoming object. For example, an admission webhook or mutating policy may inject a sidecar container or apply a default configuration.

Validating admission evaluates an object and can accept or reject it without mutating it. For example, a policy may reject a Pod that uses a prohibited image registry.

A simplified example:

```
apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  containers:
    - name: app
      image: untrusted.example.com/app:latest
```

If a cluster has an applicable policy prohibiting images from that registry, admission may reject the request. The Pod object will not be created as requested.

Admission is not the same as authorization:

- Authorization asks whether the caller may perform the operation.
- Admission asks whether the proposed change should be allowed under applicable admission logic and policy.

Admission also differs from ordinary API schema validation. Both may cause a request to be rejected, but they serve different purposes.

## 2.5 Validation and persistence

The API server validates resource data against the applicable API schema and other resource-specific rules. It then processes the request and, if accepted, persists the resulting state.

A request may fail because:

- The YAML cannot be parsed.
- The API version or resource kind is unsupported.
- A field has an invalid value or type.
- A Deployment selector does not match its Pod template labels.
- Admission policy rejects the object.
- The caller lacks permission.
- A dependency, webhook, or storage operation fails.

A successful API response means the requested API operation succeeded according to that operation's semantics. It does not mean the application is already running or ready.

For example:

```
kubectl apply -f deployment.yaml
kubectl get deployment
kubectl get pods
```

The first command may succeed while the Pods are still being scheduled, images are being pulled, or application processes are starting.

This distinction becomes critical during incident response: an API-level success and an application-level success are different milestones.

# 3. etcd: the persistent state store

`etcd` is a distributed, strongly consistent key-value store used by Kubernetes to persist API data. It is a foundational part of the control plane because the API server needs a durable representation of the resources that define cluster state.

For example, Kubernetes API data includes objects such as:

- Deployments and ReplicaSets.
- Pod objects and their recorded status.
- ConfigMaps and Secrets.
- Services and EndpointSlices.
- Nodes and Namespaces.
- Custom resources defined through CRDs.

The exact stored representation is an implementation detail; clients should use the Kubernetes API rather than treating etcd as an application-facing database.

## 3.1 How the API server and etcd interact

kubectl / controllers / operators

API clients

kube-apiserver

API processing, access control, resource handling and storage integration

etcd

Durable Kubernetes API state

The API server mediates access to the Kubernetes API and its storage. Ordinary users and controllers do not normally query or update etcd directly.

This architecture provides a consistent interface for clients and allows the API server to enforce API semantics and access controls.

## 3.2 Why not allow controllers to write directly to etcd?

Suppose a controller could update a Deployment record directly in etcd. That would bypass the normal API processing path, including the validation and admission behavior associated with the relevant API operation.

It would also couple the controller to internal storage representations instead of the supported Kubernetes API contract.

By interacting through the API server, controllers can use the same API mechanisms as other clients. They observe resource changes and submit updates through a standardized interface.

Operational rule: use `kubectl`, supported Kubernetes clients, or the appropriate API interface to manage resources. Directly editing etcd is not a normal troubleshooting or application-management technique.

## 3.3 What happens if etcd is unavailable?

If the API server cannot perform required storage operations, requests that need those operations may fail or become unavailable. The cluster may be unable to reliably accept new desired-state changes or persist status updates.

However, it is important to distinguish control-plane availability from already-running workload processes.

A container that is already running on a worker node does not necessarily stop merely because the API server or etcd becomes unavailable. The kubelet and container runtime may continue operating existing workloads locally. New scheduling decisions, API-driven changes, and other control-plane-dependent actions can be impaired.

The precise impact depends on what has failed, the duration of the outage, and the workload's dependencies.

This is one reason resilient control-plane design matters. In a managed Kubernetes service, much of this infrastructure is operated by the provider, but application availability still depends on workload design and the health of the worker infrastructure.

# 4. The scheduler: deciding where a Pod should run

The Kubernetes scheduler, `kube-scheduler`, assigns unscheduled Pods to suitable nodes.

The scheduler does not normally start the containers itself. Instead, it selects a node for a Pod and records that scheduling decision through the Kubernetes API. The kubelet on the selected node then takes responsibility for making the assigned Pod run.

## 4.1 Why scheduling is necessary

Consider a cluster with three worker nodes:

- `worker-a`: 2 CPUs available for scheduling.
- `worker-b`: 1 CPU available for scheduling.
- `worker-c`: insufficient remaining memory for the Pod.

A newly created Pod requests 1 CPU and 1 GiB of memory. The scheduler must evaluate which nodes are eligible and choose an appropriate placement.

This decision is not simply a matter of selecting the node with the most free resources. Kubernetes scheduling considers resource requests, constraints, policies, and other relevant factors.

## 4.2 Scheduling lifecycle

1

Pod created

The API object exists without an assigned node.

2

Scheduler observes Pod

The scheduler identifies a Pod requiring placement.

3

Filter candidate nodes

Nodes that violate hard requirements are excluded.

4

Score eligible nodes

Remaining nodes are evaluated using applicable scoring rules.

5

Select a node

The scheduler chooses an eligible node.

6

Record the binding

The assignment is recorded through the API.

7

Kubelet acts

The selected node's kubelet works to run the Pod.

This is a conceptual view of the normal scheduling path. Pods with custom scheduling requirements, static Pods, or other special configurations can follow different paths.

## 4.3 Scheduling filters: which nodes are eligible?

During filtering, the scheduler evaluates whether a node can satisfy the Pod's applicable requirements.

Important considerations include:

Resource requests. A Pod's CPU and memory requests affect whether a node has sufficient schedulable capacity. Requests are central to scheduling decisions; they are not a guarantee of instantaneous physical CPU or memory availability.

Node selectors and node affinity. A workload may require or prefer nodes with particular labels. For example, a GPU workload can require nodes labelled for GPU capability.

Taints and tolerations. A node taint can prevent Pods from being scheduled on that node unless they have a matching toleration. A toleration permits a Pod to tolerate the taint; it does not by itself force placement on that node.

Pod affinity and anti-affinity. These rules express placement relationships between Pods. They can influence whether Pods should be colocated or separated.

Topology spread constraints. These can help distribute Pods across topology domains, such as zones or nodes, according to the configured constraints.

Volume and other scheduling constraints. Storage topology, volume binding, ports, and other relevant conditions can restrict eligible nodes.

A Pod can therefore remain unscheduled even when the cluster appears to have unused CPU or memory.

## 4.4 Filtering versus scoring

The scheduler's logic is often explained as two conceptual stages:

- Filtering: determine which nodes are eligible.
- Scoring: rank the eligible nodes using applicable scoring plugins and rules.

Suppose three nodes pass all hard requirements. The scheduler may score them based on resource balance, topology preferences, affinity preferences, and other enabled scheduling logic.

The highest-scoring node is a candidate for selection, but the exact result depends on the scheduler configuration and current cluster state. You should not assume that Kubernetes always chooses the node with the most free resources or the least number of Pods.

## 4.5 Why a Pod remains Pending

A Pod in `Pending` has not yet reached the normal running state. This phase can include waiting for scheduling, image preparation, or other setup work.

One common cause is that the scheduler cannot find an eligible node. Inspect the Pod and its events:

```
kubectl get pods -n production
kubectl describe pod <pod-name> -n production
kubectl get nodes
kubectl describe node <node-name>
```

A scheduling event might indicate that no nodes satisfy a resource request or placement constraint.

For example, if all eligible nodes lack sufficient allocatable CPU for the Pod's requests, the scheduler may leave the Pod unscheduled. The correct remedy could be to add capacity, adjust unrealistic requests, or revise constraints—depending on the actual requirements.

Do not immediately conclude that a `Pending` Pod needs to be restarted. First determine whether it is waiting for a legitimate dependency or is blocked by an unsatisfied condition.

# 5. Controllers: continuously reconciling desired state

Controllers are among the most important ideas in Kubernetes.

A controller is a control loop that observes resource state, compares it with the intended state, and takes actions to reduce the difference.

Kubernetes is not a one-time deployment script. Many of its components continuously observe state and respond to changes.

## 5.1 The reconciliation loop

Observe

Read relevant resources and their current conditions

Compare

Determine the difference between desired and observed state

Act

Create, update, delete, or otherwise coordinate resources

Observe again

Check the result and repeat while reconciliation is needed

The cycle continues as events occur and state changes.

Controllers commonly use cached observations and watch events to react efficiently, and they may retry work after failures. A controller's observation is not necessarily an instantaneous, globally synchronized snapshot of every component's state.

That is why reconciliation is normally designed to be repeatable. A controller should be able to retry work without assuming that every previous attempt completed successfully.

## 5.2 Example: a Deployment requests three replicas

Consider this Deployment:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      containers:
        - name: api
          image: nginx:1.28
```

The desired replica count is three. Kubernetes manages a hierarchy of objects to work toward that state.

Deployment

Declares desired rollout and replica configuration

ReplicaSet

Maintains the desired number of matching Pods

Pod 1

Pod 2

Pod 3

The Deployment controller manages the Deployment-to-ReplicaSet relationship, including rollout behavior. The ReplicaSet controller ensures the appropriate number of Pods exists. The scheduler and kubelets participate in placing and running those Pods.

This illustrates an important architectural property: Kubernetes behavior is distributed across multiple cooperating control loops rather than implemented as one giant controller.

## 5.3 What happens when a Pod is deleted?

Suppose the Deployment has three desired replicas and all three Pods are running. Someone deletes one Pod:

```
kubectl delete pod <pod-name> -n production
```

The deletion request affects that Pod object. The ReplicaSet controller subsequently observes that fewer matching Pods exist than desired and attempts to create a replacement.

Conceptually:

1. The Pod deletion is accepted and the object proceeds through its deletion lifecycle.
2. The controller's observations reflect that the ReplicaSet has fewer usable matching Pods than desired.
3. The ReplicaSet controller requests creation of a replacement Pod.
4. The scheduler selects a node for the replacement, if it is schedulable.
5. The kubelet on that node works to run it.
6. Readiness depends on the container and application becoming healthy under the configured probes.

A replacement Pod is a new Pod object, generally with a different name and UID. Kubernetes does not resurrect the original Pod as if nothing happened.

Also, the replacement is not guaranteed to become ready immediately. If no eligible node exists or the image cannot be pulled, the desired state may remain unmet.

## 5.4 Why controllers must be idempotent and retryable

In distributed systems, operations can fail partway through or responses can be lost. A controller might issue a request but fail to receive confirmation, leaving uncertainty about whether the operation completed.

A robust reconciliation loop must handle such uncertainty.

For example, before creating a resource, a controller should account for the possibility that a previous attempt already created it. Controllers typically use API observations, resource identity, and conflict-handling logic to converge toward the target state rather than blindly repeating non-idempotent side effects.

This is why a Kubernetes controller is better understood as a continuously operating control loop than as a script that executes each deployment step exactly once.

## 5.5 Controllers do not guarantee convergence under every condition

Controllers attempt to make progress, but they cannot overcome every external limitation.

A Deployment might remain below its desired replica count because:

- The cluster lacks sufficient capacity.
- The image does not exist or cannot be downloaded.
- A policy rejects the Pod.
- Required storage cannot be attached.
- The container repeatedly crashes.
- A readiness probe keeps failing.
- An external dependency is unavailable.

The controller may continue retrying, but retrying is not the same as succeeding. The desired and observed states can remain different until the underlying condition changes.

# 6. kubelet and the container runtime: turning an assigned Pod into processes

The scheduler decides where a Pod should run. The kubelet on the selected node is responsible for making the assigned Pod's specification take effect on that node.

The kubelet communicates with the API server and coordinates with the container runtime through the Container Runtime Interface (CRI). The runtime manages the low-level creation and execution of containers.

## 6.1 Responsibilities of the kubelet

The kubelet performs node-level work that includes:

- Observing Pods assigned to its node.
- Ensuring required containers are created and running as specified.
- Coordinating image preparation through the runtime.
- Reporting Pod and container status.
- Managing configured container health checks and responding to their results.
- Coordinating volume setup and other Pod-related node operations.

The kubelet does not replace the scheduler. It acts on Pods assigned to its node rather than deciding the cluster-wide placement of every workload.

## 6.2 The CRI boundary

Kubernetes uses the Container Runtime Interface to communicate with supported container runtimes. `containerd` is a common runtime in Kubernetes environments, including many EKS node configurations.

A simplified view:

kubelet

Pod-level node management

CRI interface

Runtime communication contract

Container runtime

Container creation, execution and lifecycle management

The runtime is responsible for container execution, but a functional Pod involves more than starting one process. Networking, volumes, sandbox setup, security configuration, and other node-level components may also be involved.

The exact sequence depends on the Pod specification and the cluster's configuration.

## 6.3 A Pod is not the same thing as a container

A Pod is the smallest deployable unit in the Kubernetes API. It can contain one or more containers that share certain resources, such as a network namespace and configured volumes.

When a Pod has multiple containers, the kubelet and runtime coordinate the lifecycle of those containers within the Pod. A Pod may also have init containers and sidecar-style containers, depending on the workload design.

For a conventional single-container application, the distinction can seem academic. In production debugging, it matters because:

- A Pod object can exist before its container starts.
- A container can start and then crash.
- A Pod can have running containers but not be ready to receive traffic.
- A Pod can be assigned to a node but fail during volume setup or sandbox creation.

A Pod object existing in the API is not proof that a usable application process exists.

# 7. Following one Deployment through the whole control plane

Now combine the preceding components into a single lifecycle.

Suppose you submit a Deployment with three replicas.

## 7.1 End-to-end sequence

### 1. Manifest submission

kubectl sends the requested Deployment change to the API server.

### 2. API processing

Authentication, authorization, admission, validation and request processing occur as applicable.

### 3. Persistence

The accepted Deployment state is persisted through the API server's storage layer.

### 4. Deployment reconciliation

The Deployment controller observes the desired replica and rollout configuration.

### 5. ReplicaSet reconciliation

The controller creates or updates a ReplicaSet to represent the target Pod template and replica count.

### 6. Pod creation

The ReplicaSet controller creates Pod objects as needed.

### 7. Scheduling

The scheduler selects eligible nodes for unscheduled Pods.

### 8. Node execution

Each selected node's kubelet coordinates Pod setup and container execution.

### 9. Status reporting

Node-level and controller observations are reflected in API status.

### 10. Readiness and traffic

Once application readiness and service-discovery conditions are met, the application can receive traffic through its configured networking path.

This is a logical sequence, not a promise that every step runs synchronously or that status changes occur in a perfectly linear order. Some activities overlap, controllers observe changes asynchronously, and retries can occur at several stages.

## 7.2 Which component is responsible when something fails?

| Symptom                                      | Likely area to investigate first                                                                |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `kubectl apply` is forbidden                 | Authentication identity and authorization rules                                                 |
| Request is rejected by policy                | Admission configuration and policy diagnostics                                                  |
| Deployment exists but no Pods are created    | Deployment/ReplicaSet controllers, events, quotas and admission                                 |
| Pod exists but has no assigned node          | Scheduler events, resource requests, affinity, taints and topology constraints                  |
| Pod is assigned but container is not running | Kubelet, runtime, image pull, volume and sandbox setup                                          |
| Container runs but repeatedly exits          | Application logs, command, configuration and dependencies                                       |
| Container runs but Pod is not ready          | Readiness probe, application health and required dependencies                                   |
| Pod is ready but application is unreachable  | Service selectors, EndpointSlices, networking, policies and ingress/load-balancer configuration |

These are starting points, not exclusive mappings. A symptom can have multiple causes, so inspect events, status, logs, and related resources before changing the system.

# 8. API acceptance, Pod phase, container state, and readiness

One of the most common Kubernetes troubleshooting mistakes is treating all status indicators as if they mean the same thing.

They do not.

A successful API request, a `Running` Pod, a running container, a ready Pod, and a reachable application represent different conditions.

## 8.1 The different milestones

| Milestone                 | What it means                                                | What it does not prove                             |
| ------------------------- | ------------------------------------------------------------ | -------------------------------------------------- |
| API request succeeds      | The API operation succeeded                                  | That a Pod has been created or started             |
| Pod object exists         | Kubernetes has a Pod resource                                | That a node has been assigned                      |
| Pod has a node assignment | The Pod has been scheduled to a node                         | That its containers are running                    |
| Container is running      | The container process is running according to runtime status | That the application is healthy                    |
| Pod is Ready              | The Pod meets its configured readiness conditions            | That every external request path works             |
| Application is reachable  | A particular traffic path works                              | That every replica, zone, or dependency is healthy |

## 8.2 Pod phase versus container state

A Pod's `status.phase` is a high-level summary. Common phases include:

- `Pending`
- `Running`
- `Succeeded`
- `Failed`
- `Unknown`

These are not a detailed list of every possible condition. For example, `CrashLoopBackOff` is a container waiting reason commonly shown by `kubectl`; it is not a Pod phase.

Container state is tracked separately. A container can be `Waiting`, `Running`, or `Terminated`.

A Pod can have a `Running` phase while one of its containers is not ready. Therefore, seeing `Running` in `kubectl get pods` is not sufficient evidence that the workload is ready to serve requests.

## 8.3 Readiness probes and traffic

A readiness probe evaluates whether a container is ready to serve requests according to the configured check. If the Pod is not ready, Kubernetes normally excludes it from the ready backend set represented by the relevant Service endpoints.

For a typical selector-based Service, EndpointSlices represent the discovered endpoints, including relevant readiness information.

This means that a container can be running but excluded from normal Service traffic because it is not ready.

Liveness and startup probes have different purposes:

- Readiness probe: determines whether the container should be considered ready to serve traffic.
- Liveness probe: detects a container that should be restarted according to the configured failure policy.
- Startup probe: gives a slow-starting container time to initialize before liveness or readiness checks are applied as configured.

Poorly designed probes can create availability problems. For example, an overly aggressive liveness probe can repeatedly restart an application that needs more time to initialize or is temporarily slow under load.

The correct probe configuration depends on the application's lifecycle and health semantics—not just on whether a TCP port opens.

## 8.4 Useful commands for inspecting status

```
# Inspect high-level Pod status
kubectl get pods -n production -o wide

# Inspect events and conditions
kubectl describe pod <pod-name> -n production

# Inspect detailed Pod specification and status
kubectl get pod <pod-name> -n production -o yaml

# Inspect logs from a container
kubectl logs <pod-name> -n production

# Inspect the previous container instance after a restart
kubectl logs <pod-name> -n production --previous

# Inspect Deployment rollout status
kubectl rollout status deployment/payments-api -n production

# Inspect Service and EndpointSlice resources
kubectl get service,endpointslice -n production
```

Use the outputs together. `describe` is often useful for events and conditions, while YAML provides detailed fields such as `spec`, `status`, container states, and probe configuration.

# 9. Distributed control plane: asynchronous communication and eventual convergence

Kubernetes is a distributed system. Its components do not share one instantaneous view of the cluster, and a change submitted to the API does not cause every component to update at precisely the same moment.

Understanding this property helps explain why temporary inconsistencies in status are normal.

## 9.1 Why state changes are asynchronous

Imagine that you scale a Deployment from three replicas to five:

```
kubectl scale deployment payments-api \
  --replicas=5 -n production
```

The API server processes the requested change. The Deployment controller then observes the new desired state and works toward it. The ReplicaSet controller creates additional Pods, and the scheduler assigns those Pods to eligible nodes.

During this process, different observations can temporarily report different counts.

For example:

- Desired replicas: 5
- Current replicas: 4
- Ready replicas: 3

These values do not necessarily indicate a bug. They may indicate that reconciliation is in progress, or that one or more Pods cannot become ready.

The important task is to determine whether the system is making progress and, if not, which constraint is preventing convergence.

## 9.2 Desired state is not the same as observed state

For a Deployment, the `spec` describes the requested configuration. The `status` reports observed conditions and progress.

A controller uses its observations to decide what to do next. It does not simply assume that its last requested action succeeded.

This is fundamental to the Kubernetes design:

- A request expresses intent.
- The API server accepts or rejects the request.
- Controllers and node components act on the accepted state.
- Status reports the progress and results of those actions.
- Subsequent reconciliation continues until the system converges or encounters a condition that prevents progress.

Convergence is a goal, not an unconditional guarantee. If the cluster lacks capacity or the application cannot start, the system can remain in a non-converged state.

## 9.3 Watches, caches, and retries

Kubernetes API clients can list resources and watch for changes. Controllers commonly use local caches populated from these mechanisms to reduce unnecessary API calls and respond to events.

A watch stream can end because of connection interruptions or resource-version limitations. A well-designed client must recover, often by re-establishing its watch and relisting when necessary.

This has several implications:

1. A watch event is not a permanent guarantee that no later change occurred.
2. A controller's cached state can temporarily lag behind the API server.
3. A successful API request may be observed by another component slightly later.
4. Retries and reconciliation are normal, not exceptional, aspects of cluster operation.

When developing controllers or operators, this is why you must design around changing state, retries, and concurrent updates instead of assuming a single, strictly sequential workflow.

# 10. Control-plane failure versus worker-node failure

The control plane and worker nodes have different responsibilities, so failures in these areas produce different symptoms.

## 10.1 Control-plane failure

A control-plane failure can affect API availability, persistence, scheduling, or controller progress, depending on the affected component.

For example:

- An API server outage can prevent clients and controllers from using the Kubernetes API.
- A storage outage can prevent reliable persistence of API changes.
- A scheduler outage can prevent newly created unscheduled Pods from receiving normal scheduling assignments.
- A controller-manager outage can delay or prevent the affected controllers from reconciling their resources.

Already-running containers may continue executing during some control-plane outages. However, the cluster can lose the ability to perform normal control-plane operations or react promptly to failures.

## 10.2 Worker-node failure

If a worker node becomes unavailable, the workloads on it may stop responding, even if the control plane remains healthy.

The control plane may observe the node's unhealthy condition and, depending on the workload and configured behavior, coordinate recovery by creating replacement Pods or scheduling workloads elsewhere.

However, recovery is subject to several conditions:

- Sufficient capacity must exist on other eligible nodes.
- Storage and topology constraints must permit relocation.
- The workload's controller must support the required recovery behavior.
- Application availability depends on how many replicas remain healthy and how traffic is routed.

For example, a Deployment with three replicas spread across suitable failure domains can tolerate some individual Pod failures more effectively than a single-replica workload. But three replicas all placed on one node do not provide equivalent protection against that node's failure.

## 10.3 Managed Kubernetes and EKS

In Amazon EKS, AWS manages the Kubernetes control plane, including the service's control-plane infrastructure. You remain responsible for your workload architecture and the worker compute and surrounding configuration that you operate.

This separation reduces the burden of running the Kubernetes control plane yourself, but it does not eliminate operational responsibilities such as:

- Setting suitable CPU and memory requests.
- Designing replica counts and topology distribution.
- Managing node capacity and scaling.
- Configuring health probes.
- Monitoring scheduling failures and application errors.
- Handling networking, IAM permissions, storage, and workload security.

A managed control plane is not a guarantee that applications will remain available under every failure scenario.

# 12. Common misconceptions to eliminate

| Misconception                                                    | Correct understanding                                                                                                              |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| The API server starts containers.                                | It processes API requests. The scheduler, controllers, kubelet, and runtime perform their respective parts of workload management. |
| etcd runs the cluster.                                           | etcd persists API state; other components interpret that state and act on it.                                                      |
| The scheduler starts Pods.                                       | It selects nodes for unscheduled Pods and records placement decisions.                                                             |
| A Deployment directly manages containers.                        | A Deployment manages rollout and ReplicaSet state; ReplicaSets manage the desired number of Pods.                                  |
| `kubectl apply` success means the application is healthy.        | It means the API operation succeeded, not that scheduling, startup, readiness, and traffic routing have succeeded.                 |
| A running Pod is always ready.                                   | Pod phase and readiness are different concepts.                                                                                    |
| A toleration forces a Pod onto a node.                           | A toleration permits the Pod to tolerate a matching taint; other placement rules still apply.                                      |
| Controllers run once when an object is created.                  | Controllers continuously reconcile state and may retry actions.                                                                    |
| Kubernetes always restores the desired state immediately.        | Controllers attempt to converge, but capacity shortages, policies, dependencies, and other failures can prevent progress.          |
| A managed EKS control plane guarantees application availability. | Application availability also depends on worker capacity, workload design, dependencies, networking, and recovery behavior.        |

## Core concepts

1. Control plane: coordinates the cluster's desired state through API processing, persistence, scheduling, and reconciliation.
2. API server: the primary API entry point. It processes requests and mediates access to Kubernetes API data.
3. Authentication: establishes the caller's identity.
4. Authorization: evaluates whether the caller can perform the requested operation.
5. Admission control: can mutate or reject applicable requests before persistence.
6. etcd: provides persistent storage for Kubernetes API state.
7. Scheduler: selects suitable nodes for unscheduled Pods based on resource requirements and placement constraints.
8. Controllers: continuously compare desired and observed state and take actions to reduce the difference.
9. kubelet: manages assigned Pods on its node and coordinates with the container runtime.
10. Container runtime: creates and manages containers through the supported runtime interface.
11. Asynchronous reconciliation: API changes and observed workload outcomes occur at different times.
12. Readiness: a separate condition from API acceptance, Pod phase, and container execution.

## End-to-end mental model

Declare intent

Manifest / kubectl

Accept and persist state

API server / etcd

Reconcile and place workloads

Controllers / scheduler

Execute on nodes

kubelet / runtime

Observe actual outcomes

Status / conditions / events / readiness

Controllers continue reconciling while the desired state remains unmet.
