## 1. Why does Kubernetes exist?

### 1.1 The problem with running applications on individual servers

Consider a backend application built with Python and FastAPI. Initially, you deploy it on one Linux server, install its dependencies, configure the application, and run it as a process.

For a small application, this approach can be sufficient. However, as traffic increases and the application becomes business-critical, several operational problems emerge.

1. Problem 1: Application availability. If the server fails, the application becomes unavailable. Someone or some automated mechanism must detect the failure and restore the application on a healthy server.

2. Problem 2: Scaling. When traffic increases, one application instance may not have sufficient CPU, memory, or request-processing capacity. You may need multiple application instances distributed across several servers.

3. Problem 3: Scheduling. Once you have multiple servers, you must decide where each application instance should run. Placement depends on available resources, hardware constraints, affinity rules, and other operational requirements.

4. Problem 4: Service discovery and networking. When an application has multiple instances, clients need a stable way to reach them without tracking individual server addresses manually. Applications also need reliable communication with databases, caches, and other services.

5.  Problem 5: Failure recovery. An application process can crash even when its server remains healthy. A server can fail while the application is functioning correctly. The system needs to distinguish between these failures and respond appropriately.

6. Problem 6: Configuration consistency. Deploying applications manually across multiple servers can introduce differences in software versions, environment variables, dependencies, and runtime configuration.

7. Problem 7: Rolling updates and rollbacks. Updating an application without interrupting service requires coordinating new and old versions, monitoring readiness, and controlling how traffic shifts between instances.

These problems are not unique to containers. They existed in distributed application deployments before containers became widespread.

### 1.2 Why containers alone do not solve the problem

Containers package an application and its userspace dependencies into an isolated execution environment. They improve portability and consistency, but they do not independently provide a complete distributed application management system.

Suppose you run this command on a Linux server:

```
docker run -d -p 8000:8000 my-fastapi-app
```

The container runtime starts the container according to the requested configuration. However, the command alone does not establish a complete multi-server orchestration system.

You still need answers to questions such as:

- What happens if the container exits?
- What happens if the entire server becomes unavailable?
- How do you maintain three instances across multiple servers?
- How do other applications discover the instances?
- How do you replace old instances without causing an outage?
- How do you manage application configuration consistently?

A container runtime and an orchestration system solve different layers of the problem.

### 1.3 What Kubernetes contributes

Kubernetes is an open-source system for managing containerized workloads and associated resources through a cluster of machines.

It provides mechanisms for describing application workloads, placing them on suitable nodes, maintaining desired workload state, discovering services, configuring networking, managing storage integration, and coordinating application updates.

The important distinction is that Kubernetes does not simply execute a command to start a container. It manages a distributed system in which multiple components continuously work toward the state specified by the user.

For example, you can declare that a Deployment should maintain three replicas of an application. Kubernetes has controllers and node-level components that cooperate to make that desired state a reality and respond when the observed state changes.

Kubernetes is not a guarantee that applications can never fail. Instead, it provides mechanisms for detecting and responding to certain failures, subject to the application's configuration, the health of the cluster, and the available infrastructure.

Official reference: [Kubernetes — What is Kubernetes?](https://kubernetes.io/docs/concepts/overview)

## 2. The evolution of application deployment

To understand why Kubernetes is designed as it is, it is useful to understand how application deployment evolved. Kubernetes did not introduce the concepts of resource isolation, distributed scheduling, or process supervision from nothing. It combines and extends ideas that emerged from earlier deployment models. 

### 2.1 Traditional deployment on physical servers

In the traditional deployment model, organizations ran applications directly on physical machines. Multiple applications might share a server, or each application might have a dedicated server.

This model had several limitations.

1. Resource allocation was inflexible. If one application consumed most of a server's CPU or memory, other applications on the same machine could experience resource contention.
2. Isolation was limited. Applications running directly on the same operating system could interfere with each other through shared dependencies, files, ports, or system configuration.
3. Provisioning was slow. Obtaining and configuring additional physical machines could require significant time and operational effort.
4. Utilization could be poor. A server dedicated to a low-traffic application might remain underutilized while another application required additional capacity.

Virtualization improved this model by allowing multiple virtual machines to run on a physical host, with each VM providing its own guest operating system and isolation boundary.

### 2.2 Virtual machines

A virtual machine uses a hypervisor to virtualize hardware resources. Each VM typically runs its own operating system kernel, operating-system services, libraries, and application processes.
 
VMs provide strong isolation boundaries and allow different operating systems or kernel configurations to coexist on the same physical host. However, each VM carries the overhead associated with its operating system and associated services.

This does not mean VMs are inherently inefficient or obsolete. They remain widely used and are often the infrastructure on which Kubernetes nodes themselves run.

### 2.3 Containers

Containers use operating-system-level isolation rather than requiring a separate guest kernel for every container. On Linux, container isolation and resource management rely on kernel mechanisms such as namespaces and cgroups.

- Namespaces provide views that isolate resources such as process IDs, network interfaces, mount points, and hostnames.
- Control groups (cgroups) account for and constrain resource consumption, including CPU and memory, subject to the configured hierarchy and controls.
- Container images package application files, libraries, and other userspace dependencies into reusable image layers.

A container generally shares the host's Linux kernel, unlike a VM that normally has its own guest kernel. Consequently, containers are not identical to VMs in their isolation model.

Containers improve application packaging and deployment consistency, but a container is not itself a distributed orchestration platform. Managing a large number of containers across multiple machines still requires scheduling, service discovery, failure handling, and coordination.

### 2.4 Container orchestration

Container orchestration systems manage workloads distributed across a set of machines. They automate tasks such as placing workloads, tracking their state, responding to failures, and coordinating updates.

Kubernetes provides this functionality through a cluster architecture and an API-driven control system.

### Deployment evolution

Physical servers : Applications share machine resources directly.

Virtual machines : Hardware virtualization and separate guest operating systems.

Containers : Application packaging and operating-system-level isolation.

Kubernetes : Cluster-level workload management, scheduling, and reconciliation.

## 3. What is Kubernetes, technically?

Kubernetes is an API-driven platform that manages containerized workloads and related resources through a cluster. Users and external systems express their intentions through the Kubernetes API, and Kubernetes components cooperate to make the observed cluster state approach those intentions.

This definition contains several important ideas.

### 3.1 Kubernetes is a platform, not a container runtime

Kubernetes does not normally execute the low-level operations required to create Linux containers itself. It delegates container execution to a compatible container runtime through the Container Runtime Interface (CRI), using node-level components such as the kubelet.

For example, containerd can be used as a container runtime in a Kubernetes cluster. The kubelet communicates with the runtime through CRI to manage Pod sandboxes and containers.

This separation is important because Kubernetes can manage workloads while supporting different compatible runtime implementations.

### 3.2 Kubernetes is API-driven

Kubernetes exposes an HTTP API through the API server. Users commonly interact with it through `kubectl`, but controllers, operators, automation tools, and other components can also interact with the API.

The API provides a common interface for creating, reading, updating, watching, and deleting Kubernetes resources.

For example, a Deployment manifest describes the desired characteristics of an application workload. Submitting that manifest to the API creates or updates a Kubernetes API object. Other components observe the resulting state and perform the actions necessary to implement it.

The API server is therefore not merely a command-line gateway. It is a central coordination point for Kubernetes API operations.

### 3.3 Kubernetes uses a cluster model

A Kubernetes cluster consists of a control plane and worker nodes. The control plane manages the cluster's state and coordinates workload placement, while worker nodes provide the environment in which Pods run.

A cluster can have one or more worker nodes. Production clusters commonly use multiple nodes and may distribute control-plane components across multiple machines for availability.

The logical architecture is independent of whether the underlying machines are physical servers, virtual machines, or cloud instances. A managed service such as Amazon EKS also follows this cluster model, although the cloud provider manages certain infrastructure and control-plane responsibilities for you.

Reference: [Kubernetes cluster architecture](https://kubernetes.io/docs/concepts/architecture).&#x20;\

## 4. Declarative configuration versus imperative commands

This distinction is fundamental to understanding Kubernetes.

### 4.1 Imperative approach

In an imperative approach, the user specifies the action that should be performed.

For example:

```
kubectl create deployment api --image=nginx
kubectl scale deployment api --replicas=3
```

The first command requests the creation of a Deployment. The second requests a change to its replica count.

Imperative commands can be useful for experiments, troubleshooting, and one-off operations. However, a sequence of commands does not necessarily provide a complete, version-controlled description of the application's intended configuration.

### 4.2 Declarative approach

In a declarative approach, the user specifies the intended state of a resource rather than enumerating every operation required to reach that state.

For example:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: nginx
          image: nginx:1.28
          ports:
            - containerPort: 80
```

This manifest describes a Deployment named `api` whose desired replica count is three. It also defines a Pod template specifying the container image and associated configuration.

The manifest does not tell the scheduler which specific node to select, how the kubelet should create the container, or which low-level system calls should be made. Those responsibilities belong to Kubernetes components and the container runtime.

The manifest specifies the desired outcome; Kubernetes implements that outcome through its control processes.

### 4.3 Declarative does not mean that no actions occur

A common misconception is that declarative systems do not execute commands or perform operations. In reality, Kubernetes performs many actions in response to declarative specifications.

The distinction is where the primary responsibility lies.

In an imperative workflow, the user explicitly directs a sequence of operations. In a declarative workflow, the user specifies the intended state, and the platform determines which operations are needed to approach it.

Kubernetes does not eliminate imperative operations entirely. Administrators can use imperative commands, and controllers still perform concrete actions. Declarative configuration is a major interaction pattern, not a claim that every operation in the system is declarative.

## 5. Desired state, current state, and observed state

### 5.1 Desired state

The desired state is the configuration or outcome that a user or another control process intends the system to achieve.

For a Deployment, desired state may include:

- The number of replicas.
- The Pod template.
- The container image.
- Resource requests and limits.
- Labels and selectors.
- Other workload configuration and policies.

In a Kubernetes API object, desired configuration is commonly represented in the `spec` field.

### 5.2 Current state

The current state refers to the conditions and resources that actually exist in the system at a given time.

For example, a Deployment may specify three replicas, but only two Pods may currently be available because a node has failed or a new Pod cannot be scheduled.

The current state may therefore differ from the desired state.

### 5.3 Observed state

The observed state is the information a component has obtained about the system through its observations.

This distinction matters because Kubernetes controllers do not have omniscient, instantaneous knowledge of the entire cluster. Components observe resources through API reads, watches, caches, events, and other mechanisms, depending on their implementation.

The observed state may lag behind reality. Controllers can also observe different parts of the system at different times.

Consequently, Kubernetes is not a system in which all components share one perfectly synchronized, instantaneous picture of reality. It is a distributed control system that continuously reacts to observed changes.

### 5.4 `spec` and `status`

Many Kubernetes objects expose two especially important fields:

- `spec` describes the desired characteristics of the resource.
- `status` reports information about the resource's observed or current condition.

For example, a Deployment's specification may request three replicas, while its status reports how many replicas have been observed as created, ready, or available.

The precise status fields depend on the resource type.

An important technical detail is that `status` is not a universal, perfect representation of every underlying runtime fact. It is API-reported state maintained by Kubernetes components, and its freshness and meaning depend on the resource and field in question.

The distinction between specification and status makes it possible to represent an intention separately from the system's progress toward fulfilling it.

## 6. Reconciliation: the central design principle

Reconciliation is one of the most important concepts to understand before studying Kubernetes internals.

A reconciliation loop is a control process that repeatedly observes the system, compares the observed state with the intended state, and takes actions to reduce the difference.

This pattern is used in many systems, including thermostats, infrastructure controllers, distributed databases, and Kubernetes controllers.

### 6.1 Understanding reconciliation with a thermostat

Suppose you set a thermostat to maintain a room temperature of 22°C.

- The desired state is 22°C.
- The observed room temperature is 18°C.
- The controller observes the difference and activates heating.
- The temperature rises, and the controller observes the new temperature.
- The controller adjusts its behavior as needed to approach the target.

The controller does not need to execute a complete, fixed sequence of operations that assumes the room temperature will change exactly as predicted. It repeatedly observes conditions and responds to them.

Kubernetes applies a similar pattern to cluster resources, although its controllers operate on distributed software resources rather than physical temperature.

### 6.2 Reconciliation in Kubernetes

Suppose a Deployment specifies three replicas.

Initially, there may be no corresponding Pods. A controller observes the Deployment and works toward creating the required ReplicaSet and Pods. Other controllers and node components cooperate to schedule and run those Pods.

Now suppose one of the three Pods disappears.

The system observes that the actual number of replicas no longer matches the desired number. The appropriate workload controllers respond by creating a replacement Pod, assuming the required resources and dependencies are available.

The controller does not directly run the container on a machine. It changes Kubernetes API resources, and other components respond to those changes.

This distinction is fundamental: a Kubernetes controller usually coordinates through the API rather than directly executing all the operations required to run a workload.

### 6.3 A simplified reconciliation model

1\. Observe state

Read the relevant resources and conditions.

2\. Compare states

Determine whether action is needed.

3\. Take corrective action

Create, update, or delete relevant resources.

4\. Observe again

Evaluate the result and continue reconciling.

Conceptual control loop; real controllers have implementation-specific event handling, queues, retries, and synchronization behavior.

### 6.4 Why reconciliation is powerful

Reconciliation makes the system resilient to many kinds of change.

1. It handles unexpected changes. Controllers can respond when resources disappear or conditions change after the original deployment.
2. It reduces dependence on fixed execution sequences. A controller can repeatedly evaluate the current situation instead of assuming that each earlier operation succeeded permanently.
3. It supports independent components. Different controllers can manage different aspects of the system and coordinate through shared API resources.
4. It supports eventual convergence. Under suitable conditions, controllers can move the system toward the desired state even if intermediate operations fail.

However, reconciliation does not guarantee that every desired state will eventually be achieved. Insufficient capacity, invalid configuration, unavailable dependencies, permission problems, or failed infrastructure can prevent convergence.

Kubernetes controllers also do not all share one universal loop implementation. Their exact responsibilities and behavior depend on the controller.&#x20;

## 8. What happens when you deploy an application?

Consider the following simplified lifecycle for a Deployment with three replicas.

1. You write a YAML manifest specifying the desired Deployment configuration.
2. You submit it through `kubectl`, which sends an API request to the API server.
3. The API server processes the request, including applicable authentication, authorization, validation, admission, and persistence steps.
4. The Deployment controller observes the new Deployment and creates or updates the corresponding ReplicaSet.
5. The ReplicaSet controller creates Pod objects as necessary to satisfy the requested replica count.
6. The scheduler selects suitable nodes for Pods that have not yet been assigned to a node.
7. The kubelet on each selected node observes the assigned Pods and coordinates with the container runtime to create the required Pod sandboxes and containers.
8. Networking and storage components provide the configured resources and connectivity.
9. The kubelet and other controllers report status, and the relevant control loops continue responding to changes.

This sequence is simplified. Some work occurs concurrently, components observe changes asynchronously, and details vary according to the resource configuration and cluster implementation.

The important point is that `kubectl apply` does not directly create the application container. It submits an API operation; multiple components then cooperate to realize the requested workload.

## 9. What Kubernetes does not do automatically

Understanding the platform's boundaries is just as important as understanding its features.

- Kubernetes does not automatically make application code fault-tolerant. Applications still need suitable error handling, timeouts, and recovery strategies.
- Kubernetes does not guarantee zero downtime. Availability depends on deployment configuration, readiness, capacity, networking, application behavior, and other factors.
- Kubernetes does not build your application source code into an image. That is normally handled by a build system or CI pipeline.
- Kubernetes does not automatically provide every database, message broker, monitoring system, or logging backend. Those services must be deployed or integrated separately.
- Kubernetes does not guarantee that every Pod will be scheduled. Scheduling can fail because of resource constraints, affinity rules, taints, or other requirements.
- Kubernetes does not replace all infrastructure management. Cluster provisioning, machine lifecycle, and cloud integrations may be handled by external systems or managed-service providers.

These limitations are important because Kubernetes is a platform for managing workloads, not a complete application development and operations solution by itself.&#x20;
