# Lesson 2 — Kubernetes Objects, API, and Declarative Resource Management

Module 1 · Foundations · Technical study notes

This lesson builds directly on Lesson 1. We established that Kubernetes manages workloads by comparing desired state with observed state and coordinating changes through controllers. Now we will examine how Kubernetes represents that state, how clients communicate with the cluster, and how an API request becomes a persistent Kubernetes object.

This is one of the most important foundations for understanding Kubernetes internals. The API server, controllers, scheduler, and kubelet all interact with Kubernetes resources, but they do not all have the same responsibilities or directly modify the same parts of an object's state.

The focus of this lesson is the API and object model, not just writing YAML manifests.

## 1. What is a Kubernetes object?

### 1.1 Definition

A Kubernetes object is a persistent representation of an entity that the Kubernetes API manages. Objects describe the desired configuration of workloads, cluster resources, and other aspects of the system.

Examples include:

- A `Pod` object describes a workload unit containing one or more containers.
- A `Deployment` object describes the desired management of a set of replicated application Pods through ReplicaSets.
- A `Service` object describes a stable network endpoint for accessing a logical set of backend Pods.
- A `ConfigMap` object stores non-confidential configuration data.
- A `Secret` object stores sensitive configuration data, although additional access controls and encryption-at-rest configuration may be necessary to protect it.
- A `Node` object represents a machine registered with the cluster.
- A `Namespace` object provides a scope for namespaced resources.

An object is not necessarily the same thing as the real-world entity it represents.

For example, a `Pod` API object and the running containers associated with that Pod are different things. The API object represents the workload's configuration and reported state. The containers are runtime processes managed on a worker node.

A Pod object can exist before any container has started. It can also remain visible in the API after the containers have terminated, depending on the Pod's lifecycle and cleanup.

### 1.2 Objects are managed through an API

Kubernetes exposes an HTTP API through the API server. Clients can use this API to create, retrieve, modify, watch, and delete objects.

`kubectl` is one such client. It provides a command-line interface that translates user operations into Kubernetes API requests.

Other clients include:

- Controllers that manage Kubernetes resources.
- Operators that implement application-specific control logic.
- CI/CD systems that deploy application configuration.
- Monitoring and automation systems that read resource state.
- Custom applications using Kubernetes client libraries.

This API-centric design provides a common interface for interacting with cluster resources.

The API server does not simply store arbitrary YAML files. It processes API requests, applies the relevant resource and policy rules, and manages the corresponding API objects.

Official reference: [Kubernetes API overview](https://kubernetes.io/docs/concepts/overview/kubernetes-api).

## 2. Anatomy of a Kubernetes manifest

Consider this Deployment manifest:

```

apiVersion: apps/v1
kind: Deployment

metadata:
  name: payments-api
  namespace: production
  labels:
    app: payments-api
    team: platform

spec:
  replicas: 3

  selector:
    matchLabels:
      app: payments-api

  template:
    metadata:
      labels:
        app: payments-api
    spec:
      containers:
        - name: api
          image: nginx:1.28
          ports:
            - containerPort: 80

```

This example describes a Deployment named `payments-api` in the `production` namespace.

The image and replica count are illustrative. In an actual deployment, you would use an application-specific image and a versioning strategy appropriate for your environment.

A Kubernetes manifest commonly contains five major fields: `apiVersion`, `kind`, `metadata`, `spec`, and sometimes `status`. The first four are generally present in a user-authored resource manifest; `status` is normally maintained by Kubernetes components.

### 2.1 `apiVersion`

The `apiVersion` field identifies the API group and version used to represent the resource.

In the example, `apps/v1` means the resource belongs to the `apps` API group and uses version `v1` of that group.

Different resource types belong to different API groups. For example:

- `v1` is used for core resources such as Pods, Services, ConfigMaps, and Secrets.
- `apps/v1` is used for resources such as Deployments, ReplicaSets, and StatefulSets.
- `batch/v1` is used for Jobs and CronJobs.

The API version matters because Kubernetes uses versioned API schemas to interpret and validate requests.

An API version is not the same as the version of the Kubernetes software binary. It identifies a version of an API representation, and different API groups can have different version histories.

### 2.2 `kind`

The `kind` field identifies the type of object being represented.

For example:

- `Deployment` identifies a Deployment resource.
- `Pod` identifies a Pod resource.
- `Service` identifies a Service resource.

The API server uses the API group, version, and kind information to determine how the resource is handled and represented through the API.

Conceptually, `kind` answers: What type of Kubernetes resource am I describing?

### 2.3 `metadata`

The `metadata` field contains information used to identify, organize, track, and relate the object to other objects.

Important metadata fields include:

| Field             | Purpose                                                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `name`            | The object's name within its applicable scope.                                                                              |
| `namespace`       | The namespace containing a namespaced resource.                                                                             |
| `labels`          | Key-value pairs used to organize and select objects.                                                                        |
| `annotations`     | Key-value metadata intended for identification, tooling, or other contextual information rather than label-based selection. |
| `uid`             | A unique identifier assigned to a particular object instance.                                                               |
| `resourceVersion` | An opaque version marker used by the API to identify a particular resource state for concurrency and change tracking.       |
| `generation`      | A sequence number associated with changes to an object's desired specification, where applicable.                           |
| `ownerReferences` | References identifying objects that own or manage the dependent object.                                                     |

Not all these fields need to be supplied in a manifest. Several are assigned or maintained by the API server or controllers.

### 2.4 `spec`

The `spec` field describes the desired characteristics of the object.

For a Deployment, the specification includes the desired replica count, selector, and Pod template.

For a Pod, the specification includes the containers and their configuration, along with other Pod-level settings.

For a Service, the specification includes information such as the Service type, port configuration, and selector when a selector is used.

The exact schema depends on the resource kind. There is no single universal set of `spec` fields shared by every Kubernetes object.

### 2.5 `status`

The `status` field contains information about the object's observed condition or progress, as defined by the resource's API.

For example, a Deployment's status may report how many replicas have been observed, are ready, or are available.

A Pod's status contains phase information and additional details about conditions and container states.

The status field is generally maintained by Kubernetes controllers or other components responsible for reporting that resource's state. A normal workload manifest should not attempt to manage runtime status as though it were part of the user's desired configuration.

A useful mental model is:

### Kubernetes object

The API representation of a resource

`spec`

What should be true.

Desired configuration

`status`

What is reported to be true.

Observed conditions

Controllers and other components act on resource specifications and update relevant status fields. The exact responsibilities vary by resource type.

Reference: [Kubernetes objects](https://kubernetes.io/docs/concepts/overview/working-with-objects/?utm_source=chatgpt.com).

## 3. Object identity: how Kubernetes identifies a resource

Understanding object identity is essential for understanding updates, deletion, recreation, and API concurrency.

### 3.1 Name and namespace

For namespaced resources, the combination of resource type, namespace, and name identifies the resource within the relevant API scope.

For example, these two objects can coexist:

- Deployment `payments-api` in namespace `production`.
- Deployment `payments-api` in namespace `staging`.

They have the same name but belong to different namespaces.

However, creating a second Deployment with the same name in the same namespace does not normally create a second independent Deployment. A create request conflicts with an existing object of that identity.

Not all Kubernetes resources are namespaced. For example, Nodes and Namespaces are cluster-scoped resources. A namespace field does not make a cluster-scoped resource namespaced.

### 3.2 UID: the identity of a particular object instance

Kubernetes assigns each object a UID, which uniquely identifies that particular object instance.

Suppose you create a Deployment named `payments-api`, then delete it and create another Deployment with the same name.

The new Deployment has the same namespace and name but a different UID.

This distinction is important because a name can be reused, while the UID distinguishes the original object from the replacement.

For example, if another resource has an owner reference to the original Deployment, Kubernetes can distinguish that original owner from a newly created Deployment that happens to have the same name.

### 3.3 `resourceVersion`: tracking resource changes

Kubernetes assigns a `resourceVersion` to API objects. It is used by the API to track resource versions for operations such as optimistic concurrency control and watching changes.

You might see output such as:

```
metadata:
  name: payments-api
  namespace: production
  uid: 7f3a-example-uid
  resourceVersion: "48291"
  generation: 4
```

These values are illustrative, not actual cluster identifiers.

The critical point is that `resourceVersion` is an opaque value, not an application-level revision number. Clients should not parse it as a meaningful integer, assume it increments globally across every object, or perform arithmetic on it.

For a particular API operation, the server uses the relevant resource-version semantics to determine whether the request is valid against the state being updated or watched.

### 3.4 `generation`: changes to desired specification

For resources that implement it, `generation` is a metadata field associated with changes to the desired specification.

For example, when you change a Deployment from three replicas to five, the API server normally increments the Deployment's generation to represent the updated desired configuration.

Controllers can report the generation they have observed or processed through fields such as `status.observedGeneration`, where supported.

This lets clients distinguish between a new desired specification and status that may still reflect an earlier generation.

The exact semantics depend on the resource type. Do not assume every Kubernetes resource has identical generation behavior.

### 3.5 Why these fields are different

| Field             | Core question it helps answer                           |
| ----------------- | ------------------------------------------------------- |
| `name`            | What is this resource called within its scope?          |
| `namespace`       | In which namespace does this namespaced resource exist? |
| `uid`             | Which particular object instance is this?               |
| `resourceVersion` | Which API resource version is being referenced?         |
| `generation`      | Which desired specification generation is represented?  |

These fields are not interchangeable. A controller or client that confuses them can mishandle object replacement, updates, or concurrent changes.

Official reference: [Kubernetes object metadata](https://kubernetes.io/docs/reference/kubernetes-api/definitions/object-meta-v1-meta/?utm_source=chatgpt.com).

## 4. What happens when you submit a YAML manifest?

A YAML manifest is a human-readable representation of a resource definition. Kubernetes does not simply save the text file and execute it as a script.

When you run:

```
kubectl apply -f deployment.yaml
```

the client and API server participate in a series of operations.

### 4.1 The request lifecycle

1\. YAML manifest

The user defines the intended resource.

2\. kubectl

Loads configuration and constructs an API request.

3\. API server

Authenticates, authorizes, validates, and applies admission processing as appropriate.

4\. Persistence

The accepted resource state is persisted through the API server's storage layer.

5\. Controllers and other consumers

Components observe resource changes and perform their responsibilities.

This diagram shows the conceptual path. Some processing stages and implementation details are omitted, and the exact behavior depends on the API operation.

### 4.2 Client-side preparation

`kubectl` reads the manifest and determines which API resource it describes. It uses its configuration to identify the target cluster and credentials.

Depending on the command and configuration, the client may perform discovery, schema-related processing, local transformations, or other preparation before submitting the request.

The client does not have the final authority to decide whether a resource is allowed to exist in the cluster. The API server enforces server-side rules and policies.

### 4.3 Authentication

Authentication establishes the identity associated with an API request.

Depending on the cluster configuration, the API server may use mechanisms involving client certificates, bearer tokens, or configured authentication integrations.

In Amazon EKS, for example, the usual `kubectl` authentication workflow involves AWS IAM credentials and EKS authentication mechanisms. The precise implementation depends on the cluster configuration and authentication mode.

Authentication answers:

Who is making this request?

It does not, by itself, establish whether that identity has permission to perform the requested operation.

### 4.4 Authorization

Authorization determines whether the authenticated identity is allowed to perform the requested action on the relevant resource.

For example, a user may be allowed to read Deployments in one namespace but not create or delete them. Another identity may have broader permissions.

Kubernetes supports authorization mechanisms such as Role-Based Access Control (RBAC), as well as other authorizers depending on the cluster configuration.

Authorization answers:

Is this identity allowed to perform this operation?

A request can be authenticated successfully and still be rejected because the identity lacks the required permission.

### 4.5 Admission control

After authentication and authorization, API requests are subject to the applicable admission processing before persistence.

Admission controllers can validate or modify requests according to policy. Some built-in admission plugins enforce Kubernetes behavior, while admission webhooks allow external services to validate or mutate requests.

For example, a policy may reject a workload that violates an organizational requirement or mutate an accepted Pod specification to inject additional configuration.

Admission is not the same as authorization. Authorization decides whether the identity may perform an operation; admission evaluates whether the proposed object or operation is acceptable under applicable admission rules.

### 4.6 Validation and persistence

The API server validates the request against the resource schema and relevant API rules. The accepted object is processed through the API server's storage layer and persisted in etcd.

The API server does not normally hand the YAML directly to a worker node. Instead, it manages the API object and exposes its state to components that need to observe it.

After persistence, controllers and other components can observe the new resource and begin their work. Those actions are generally asynchronous relative to the original API request.

Consequently, a successful `kubectl apply` response does not necessarily mean that the application is already running or ready to receive traffic.

Reference: [Kubernetes API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/?utm_source=chatgpt.com).

## 5. The API server and etcd: how they relate

These components are closely related, but they have distinct responsibilities.

### 5.1 API server

The API server, implemented by `kube-apiserver` in a standard Kubernetes control plane, exposes the Kubernetes API.

Its responsibilities include processing API requests, enforcing relevant access and admission policies, validating resources, and coordinating their persistence and retrieval.

Clients and control-plane components use the API server as the standard interface for working with Kubernetes API resources.

### 5.2 etcd

etcd is a distributed, strongly consistent key-value store used by Kubernetes to persist cluster API data.

It stores the underlying data associated with Kubernetes API resources. The API server's storage layer translates between API-level resource operations and the storage representation.

A client should normally use the Kubernetes API rather than read or modify Kubernetes' etcd data directly. Direct etcd manipulation can bypass API validation, admission, and normal coordination mechanisms, potentially leaving the cluster in an inconsistent or unsupported state.

### 5.3 Why separate the API server from storage?

Separating the API interface from the persistence system creates a defined boundary between resource management and the underlying data store.

This allows Kubernetes clients and controllers to interact through stable API operations rather than needing to understand etcd's internal storage layout.

It also enables the API server to enforce consistent rules for reads and writes, apply authorization and admission logic, and expose resource-watch mechanisms.

### 5.4 A conceptual storage path

kubectl / API client

kube-apiserver

API processing, policy enforcement, storage coordination

etcd

Persistent key-value data

This is a simplified architecture diagram. The API server's storage implementation includes additional logic, and a production cluster may run multiple API server instances and a multi-member etcd cluster.

One important distinction is that etcd does not schedule Pods, execute containers, or independently reconcile Deployment replicas. Those responsibilities belong to other Kubernetes components.

Reference: [Kubernetes components](https://kubernetes.io/docs/concepts/overview/components/?utm_source=chatgpt.com).

## 6. How Kubernetes tracks changes: resource versions and watches

A Kubernetes cluster is dynamic. Objects are created, modified, and deleted continuously. Controllers need a mechanism for learning about these changes without repeatedly retrieving every resource from the API.

The Kubernetes API provides list and watch operations, along with resource-version semantics that allow clients to track changes.

### 6.1 List operations

A list request retrieves a collection of resources matching the requested scope and filters.

For example:

```
kubectl get deployments -n production
kubectl get pods -n production -o wide
```

These commands request resource information from the API server. The displayed output is a representation of API data; it is not a direct inspection of container processes on every node.

### 6.2 Watch operations

A watch allows a client to receive notifications about changes to API resources.

Conceptually, a controller can:

1. Obtain a list of relevant resources.
2. Establish or continue watching for changes.
3. Update its local view of the resources.
4. Enqueue work for resources that may need reconciliation.
5. Reconcile the relevant resources and their dependencies.

Watches are important because controllers must respond to changes efficiently. However, a watch is not a guarantee that every event will be delivered forever over a single uninterrupted connection. Connections can terminate, clients may need to relist, and resource-version expiration can require recovery procedures.

Well-designed Kubernetes controllers therefore use list/watch patterns and retry logic to recover from disruptions.

### 6.3 Why controllers often use caches

Controllers built with common Kubernetes libraries frequently use local caches and informers to reduce repeated API requests and efficiently observe resource changes.

A cache allows a controller to work from a local view of resources, but that view can be temporarily behind the API server's latest state.

This is why controller logic must be designed to tolerate retries, duplicate work, and changes that occur between observation and action.

### 6.4 Resource versions and watch continuity

A resource's `resourceVersion` can be used with supported API operations to establish a point from which a client wants to observe changes.

Clients must follow the API's resource-version rules rather than treating the value as a globally ordered timestamp.

If the requested history is no longer available, a client may need to retrieve a fresh list and restart watching from a suitable resource version.

This mechanism supports efficient observation of changes, but it does not eliminate the need for reconciliation. Notifications indicate that something changed; controllers still need to determine what action, if any, is required.

Official reference: [Kubernetes API concepts — resource versions and watches](https://kubernetes.io/docs/reference/using-api/api-concepts/?utm_source=chatgpt.com).

## 7. Labels, selectors, and ownership relationships

Kubernetes resources rarely operate in isolation. Deployments create ReplicaSets, ReplicaSets manage Pods, and Services commonly use selectors to identify backend Pods.

Three concepts help explain these relationships: labels, selectors, and owner references.

### 7.1 Labels

A label is a key-value pair attached to an object.

For example:

```
metadata:
  labels:
    app: payments-api
    environment: production
    team: platform
```

Labels allow objects to be grouped and selected according to meaningful attributes.

A label does not, by itself, establish ownership or cause Kubernetes to create another resource. It provides metadata that other mechanisms can use.

For example, two Pods may both have `app: payments-api` even though they were created by different controllers. Whether they are selected by a Service or managed by a particular ReplicaSet depends on the relevant selectors and ownership relationships.

### 7.2 Selectors

A selector identifies objects that match specified criteria.

For example:

```
selector:
  matchLabels:
    app: payments-api
```

This selector matches objects whose labels include `app=payments-api`.

Kubernetes supports label selectors in different forms, including equality-based matching and set-based expressions. The exact selector capabilities depend on the API field in which the selector is used.

Selectors are central to several Kubernetes features:

- A Deployment's selector identifies the Pods belonging to its ReplicaSet management hierarchy.
- A Service selector identifies Pods that should be used as its backends.
- Other controllers and API operations use selectors to identify resource sets.

A selector is a matching rule, not an ownership declaration.

### 7.3 Why Deployment selectors must match Pod labels

Consider this relationship:

Deployment

Selects Pods using `app=payments-api`

ReplicaSet

Maintains the requested replica count

Pod 1

app=payments-api

Pod 2

app=payments-api

Pod 3

app=payments-api

The Deployment selector must match the labels on its Pod template. Kubernetes validates important aspects of this configuration, and a mismatch can cause the manifest to be rejected.

A subtle but important point is that the Deployment controller does not generally create Pods directly. It manages a ReplicaSet, and the ReplicaSet controller maintains the Pods.

### 7.4 Owner references

Owner references express a resource relationship in Kubernetes metadata.

For example, a ReplicaSet created by a Deployment normally has an owner reference to that Deployment. Pods created by the ReplicaSet normally have owner references to that ReplicaSet.

This forms a management hierarchy:

```
Deployment
    |
    | owns
    v
ReplicaSet
    |
    | owns
    v
Pods
```

Owner references are different from labels and selectors.

- Labels describe attributes.
- Selectors identify resources that match criteria.
- Owner references identify a resource relationship used by Kubernetes mechanisms such as garbage collection and controller management.

Kubernetes garbage collection can use owner references when deciding whether dependent objects should be deleted after an owner is removed. The exact behavior depends on deletion propagation and ownership settings.

Owner references do not mean that every child resource is immediately deleted whenever an owner is deleted. Kubernetes supports different deletion propagation behaviors, and some objects may have special lifecycle rules.

Official references: [Labels and selectors](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/?utm_source=chatgpt.com) and [Owners and dependents](https://kubernetes.io/docs/concepts/overview/working-with-objects/owners-dependents/?utm_source=chatgpt.com).

## 8. How declarative updates work

Creating an object is only one part of Kubernetes resource management. In practice, the desired configuration of an application changes over time.

You may change the image version, increase the replica count, modify resource requests, or update environment configuration. Kubernetes must represent these changes in its API and coordinate the required actions.

### 8.1 Updating the manifest

Suppose the original Deployment specifies three replicas:

```
spec:
  replicas: 3
```

Later, you change it to five:

```
spec:
  replicas: 5
```

When you apply the updated manifest, Kubernetes processes an update to the Deployment object.

The API server does not itself start two new application containers. Instead, the updated desired specification becomes available to the Deployment controller, which works to update the ReplicaSet configuration and maintain the requested number of replicas.

Other components then participate in scheduling and running the new Pods.

### 8.2 The difference between updating a resource and reconciling it

Two separate processes are involved:

API update: The API server accepts a change to an object's desired configuration and persists the accepted resource state.

Reconciliation: Controllers observe that change and take the actions necessary to move the system toward the new desired state.

This distinction explains why an API update can succeed even if the application has not yet reached the requested state.

For example, an updated Deployment may exist in the API while its new Pods remain unscheduled because the cluster has insufficient capacity.

The desired state has been accepted, but reconciliation has not yet achieved the desired outcome.

### 8.3 `kubectl apply` and declarative configuration

`kubectl apply` is commonly used to manage resources from manifests.

Its update behavior depends on the apply mode:

- Client-side apply uses client-side logic and historically relies on the `kubectl.kubernetes.io/last-applied-configuration` annotation to track the previously applied configuration.
- Server-side apply sends structured configuration to the API server, which tracks field ownership and manages conflicts between field managers.
- Create or update operations performed through other commands or API clients may have different update semantics.

Therefore, it is inaccurate to say that every `kubectl apply` command performs the same kind of update internally.

### 8.4 Server-side apply and field ownership

Server-side apply is particularly important when multiple actors manage the same Kubernetes object.

Suppose one automation system manages a Deployment's replica count while another manages its container image. Server-side apply tracks which field manager owns which fields.

If a field manager attempts to change a field owned by another manager, Kubernetes can report a field-ownership conflict, depending on the request and the fields involved.

This is useful because it helps prevent independent automation systems from silently overwriting each other's configuration.

Field ownership is not the same as authorization. Authorization determines whether an identity may perform an operation; server-side apply field ownership helps manage conflicts over declaratively managed fields.

Reference: [Server-Side Apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/?utm_source=chatgpt.com).

## 9. Create, update, patch, and delete: API operations are not interchangeable

Kubernetes supports several kinds of API operations. Understanding their differences is important when troubleshooting resource updates and designing automation.

| Operation | General purpose                                                      | Important consideration                                                        |
| --------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `GET`     | Retrieve an object or collection.                                    | Reads the API representation, not necessarily every underlying runtime detail. |
| `LIST`    | Retrieve a collection of objects.                                    | Can be scoped and filtered using supported parameters.                         |
| `WATCH`   | Observe resource changes.                                            | Clients must handle interruptions and resource-version semantics.              |
| `POST`    | Commonly used to create resources or invoke specific API operations. | The exact behavior depends on the API endpoint.                                |
| `PUT`     | Replace an existing resource representation.                         | Replacement semantics and concurrency checks matter.                           |
| `PATCH`   | Modify part of a resource.                                           | The patch type determines how changes are interpreted.                         |
| `DELETE`  | Request resource deletion.                                           | Deletion may involve finalizers, propagation, and asynchronous cleanup.        |

These are general API concepts. Kubernetes provides additional operation-specific behavior and supports different patch formats, including JSON Patch, JSON Merge Patch, and Strategic Merge Patch where applicable.

### 9.1 Why patch types matter

A patch is not simply a shortened version of a complete manifest. Its semantics determine how the supplied changes are merged or applied.

For example, a JSON Merge Patch generally uses JSON object merge semantics, where a field set to `null` can mean removal. JSON Patch instead uses explicit operations such as `add`, `remove`, and `replace`.

Strategic Merge Patch uses Kubernetes-specific merge behavior for supported resource types and fields. It is not universally supported for every API resource, especially custom resources.

Server-side apply is another distinct mechanism, with declarative field ownership and conflict semantics.

For reliable automation, you should know which update mechanism a tool uses rather than assuming all patches behave the same way.

### 9.2 Deletion does not always mean immediate removal

When you delete a resource, the API server may initiate a deletion process rather than immediately removing every related object or runtime artifact.

Finalizers can delay the completion of deletion while controllers perform cleanup. Owner references and deletion propagation determine how dependent resources are handled.

For example, a resource with a finalizer can remain visible with a deletion timestamp while a controller performs required cleanup.

This explains why an object can appear to be "stuck terminating" even after a delete request has succeeded.

Official reference: [Kubernetes API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/?utm_source=chatgpt.com).

## 10. Custom Resource Definitions: extending the Kubernetes API

So far, we have focused on built-in Kubernetes resources such as Deployments and Services. Kubernetes also allows users to extend the API with custom resource types.

### 10.1 What is a Custom Resource Definition?

A CustomResourceDefinition (CRD) defines a new resource type that can be managed through the Kubernetes API.

For example, an organization might introduce a custom resource named `Database` to describe a database service that its platform manages.

A simplified conceptual example might look like this:

```
apiVersion: platform.example.com/v1
kind: Database
metadata:
  name: orders-db
spec:
  engine: postgres
  version: "16"
  storage: 50Gi
```

This example is illustrative. The resource will only be accepted if the corresponding CRD has been installed and its schema permits the specified fields.

The API server can then recognize instances of the new resource type according to the CRD's definition.

### 10.2 A CRD does not automatically implement the behavior

Defining a custom resource type does not automatically provide a controller that provisions databases, creates Pods, or configures storage.

A CRD defines the API schema and makes instances of that resource type available through the Kubernetes API. To implement application-specific behavior, an operator or controller typically watches those custom resources and reconciles them.

For example:

1. An administrator creates a `Database` custom resource.
2. A database operator observes the new object.
3. The operator determines what infrastructure or workload resources are required.
4. The operator creates or updates those resources.
5. The operator reports the database's status.

This is the same broad desired-state and reconciliation model introduced in Lesson 1, now applied to an API type defined by an extension.

### 10.3 Why CRDs matter

CRDs and custom controllers allow Kubernetes to manage domain-specific resources through familiar API patterns.

They are widely used by operators, cloud integrations, platform engineering systems, and infrastructure automation tools.

They also illustrate an important architectural principle: Kubernetes is extensible. Its API and reconciliation model can be used to manage resources beyond the built-in workload types.

Official reference: [Custom Resources](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/?utm_source=chatgpt.com).

## 11. Practical experiment: inspect real Kubernetes objects

Theory becomes much easier to retain when you inspect the actual API objects. Since you have already used EKS, you can run these commands against a development cluster, or use a local cluster if you prefer.

Avoid making changes to production resources during this exercise.

### 11.1 Inspect a Deployment

```
kubectl get deployments -A
kubectl get deployment <deployment-name> -n <namespace> -o yaml
```

Inspect these fields:

- `apiVersion` and `kind`.
- `metadata.name` and `metadata.namespace`.
- `metadata.uid` and `metadata.resourceVersion`.
- `metadata.generation`, if present.
- `spec.replicas` and the Pod template.
- `status.replicas`, `status.readyReplicas`, and `status.observedGeneration`, where present.

Compare the desired replica count with the reported replica counts. If they differ, investigate why instead of assuming the Deployment controller is malfunctioning.

### 11.2 Inspect the Deployment hierarchy

```
kubectl get deployments,replicasets,pods -n <namespace>
kubectl get pods -n <namespace> --show-labels
```

```
# Lesson 2: Kubernetes Objects, API, and Declarative Resource Management

## 1. Kubernetes objects
A Kubernetes object is a persistent API representation of a resource.
Examples include Pods, Deployments, Services, ConfigMaps, Secrets, and Nodes.

An API object is distinct from the runtime entity it represents. A Pod object
can exist before its containers start, and runtime processes are not themselves
the Pod API object.

## 2. Anatomy of a manifest
- apiVersion: identifies the API group and version.
- kind: identifies the resource type.
- metadata: identifies and organizes the object.
- spec: describes desired configuration.
- status: reports observed conditions or progress.

The exact schema and status semantics depend on the resource type.

## 3. Object identity and versioning
- name: identifies a resource within its applicable scope.
- namespace: scopes namespaced resources.
- uid: uniquely identifies a particular object instance.
- resourceVersion: opaque API version marker used for concurrency and watches.
- generation: tracks desired specification generations where applicable.

Names can be reused after deletion; UIDs distinguish object instances.

## 4. API request lifecycle
A client submits an API request to kube-apiserver.
The server processes authentication, authorization, validation, admission,
and persistence as applicable to the operation.

Accepted resource data is persisted through the API server's storage layer,
which uses etcd. Controllers and other components subsequently observe changes.

A successful API update does not guarantee that a workload is already running.

## 5. API server and etcd
- kube-apiserver exposes and processes the Kubernetes API.
- etcd stores persistent Kubernetes API data.
- Controllers and clients normally access resources through the API server.

Directly modifying etcd bypasses normal API processing and can leave the
cluster inconsistent or unsupported.

## 6. List and watch
LIST retrieves collections of resources.
WATCH allows clients to observe resource changes.
resourceVersion semantics help clients track resource state and changes.

Watch connections can terminate, and clients must recover from interruptions
or expired resource history. Controllers commonly use caches and informers.

## 7. Labels, selectors, and ownership
- Labels are key-value metadata.
- Selectors match resources according to criteria.
- Owner references identify resource ownership relationships.

A selector is not an ownership declaration. Owner references support
relationships and garbage collection.

A Deployment manages ReplicaSets; ReplicaSets manage Pods.

## 8. Declarative updates
An API update changes the desired configuration of an object.
Reconciliation is the subsequent process of moving the system toward it.

kubectl apply behavior depends on the apply mode.
Client-side apply and server-side apply have different mechanisms.
Server-side apply tracks field ownership and can report conflicts.

## 9. API operations
GET retrieves resources.
LIST retrieves collections.
WATCH observes changes.
POST commonly creates resources or invokes API operations.
PUT replaces a resource representation.
PATCH modifies a resource according to patch semantics.
DELETE requests resource deletion.

Finalizers and deletion propagation can delay or influence cleanup.

## 10. Custom resources
A CustomResourceDefinition (CRD) defines an additional API resource type.
A CRD alone does not implement application-specific behavior.

A controller or operator commonly watches custom resources and reconciles
their desired state, creating or updating the required resources.
```
