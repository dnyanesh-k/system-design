# Lesson 4: Kubernetes Scheduling — How Pods Get Assigned to Nodes

Module 1 · Kubernetes Foundations and Core Internals · Advanced theory with practical examples

This lesson explains how Kubernetes decides where a Pod should run, why a Pod can remain Pending even when the cluster has nodes, and how scheduling constraints influence workload placement.

Understanding scheduling is essential for production Kubernetes, particularly on AWS EKS, where node capacity, resource requests, availability zones, taints, tolerations, and autoscaling all affect workload placement.

## Learning objectives

By the end of this lesson, you should be able to:

1. Explain the responsibilities and internal workflow of the Kubernetes scheduler.
2. Distinguish scheduling from Pod execution and runtime management.
3. Explain resource requests, resource limits, and node allocatable capacity.
4. Understand scheduling filters, scoring, binding, and scheduling failures.
5. Use node selectors, node affinity, Pod affinity, and Pod anti-affinity.
6. Explain taints, tolerations, topology spread constraints, and priority.
7. Diagnose Pods stuck in the `Pending` state.
8. Apply these concepts to realistic Kubernetes and EKS workloads.

## 1. Why Kubernetes needs a scheduler

A Kubernetes cluster can contain many worker nodes, each with different amounts of CPU, memory, storage, network capacity, hardware capabilities, and failure characteristics.

When a Deployment requests five replicas, Kubernetes must determine which nodes should host those Pods. This decision cannot be based solely on which node has the fewest Pods or the most free memory. The scheduler must also respect the workload's resource requirements, placement rules, node restrictions, and cluster policies.

For example, consider a cluster with three worker nodes.

### Why simple placement strategies are insufficient

A production scheduler must account for several independent concerns:

- Resource feasibility: Can the node accommodate the Pod's requested CPU and memory?
- Hardware and environment requirements: Does the workload require a particular architecture, GPU, or node label?
- Isolation: Is the node reserved for a particular workload class?
- Availability: Should replicas be distributed across nodes or availability zones?
- Co-location: Does a workload need to run near another workload?
- Operational policy: Does the Pod have a priority, affinity rule, or other scheduling constraint?

The scheduler's job is to find a feasible placement according to Kubernetes scheduling rules. It does not guarantee that the application will subsequently start successfully or that the selected node will remain healthy.

## 2. The scheduler's place in Kubernetes architecture

The scheduler is a control-plane component. Its primary responsibility is to select a suitable node for a Pod that has not yet been assigned to one.

It is important to distinguish the scheduler from the other components involved in starting a workload.

Deployment controller

Maintains the desired number of replicas

ReplicaSet controller

Creates Pod API objects when required

Pod exists without a node assignment

The Pod is eligible for scheduling

kube-scheduler

Selects a node and initiates assignment through the API

kubelet on the selected node

Observes the assigned Pod and works to run it

Container runtime and networking

Images are pulled, containers are created, and networking is configured as required

### 2.1 What the scheduler does

The scheduler evaluates unscheduled Pods and selects nodes that satisfy their scheduling requirements. It considers resource requests, node conditions, affinity rules, taints, topology requirements, and other relevant scheduling policies.

The scheduler records its decision through the Kubernetes API. This is commonly referred to as binding the Pod to a node.

### 2.2 What the scheduler does not do

The scheduler does not directly start the application container. It does not ordinarily pull the image, launch the container process, or configure the Pod's network interface.

Those activities belong to other components, including the kubelet, container runtime, and cluster networking implementation.

This separation is fundamental:

- The scheduler decides where the Pod should run.
- The kubelet on the selected node works to make the Pod run.
- The container runtime manages the container lifecycle.
- Controllers continue reconciling their respective desired states.

A Pod can therefore be successfully scheduled but still fail to start because its image cannot be pulled, its volume cannot be mounted, or its container repeatedly crashes.

## 3. The scheduling lifecycle

Kubernetes scheduling is not a single calculation performed at the moment a manifest is submitted. It is an asynchronous process that reacts to changes in cluster state.

### 3.1 Step-by-step workflow

1. A Pod is created. A Deployment or another client causes a Pod API object to be created. Initially, the Pod may have no assigned node.
2. The scheduler observes the Pod. The scheduler identifies Pods that require scheduling, typically those without a node assignment.
3. The scheduler evaluates candidate nodes. It considers resource requirements, node eligibility, affinity, taints, topology, and other configured scheduling rules.
4. Feasible nodes are scored. If suitable nodes remain, the scheduler ranks them using scoring rules and configuration.
5. A node is selected and the Pod is bound. The scheduler records the selected node through the API server.
6. The kubelet observes the assignment. The kubelet on that node begins the work needed to realize the Pod's specification.
7. The Pod progresses through startup. Image pulling, volume setup, networking, container creation, and health checks determine whether the workload becomes ready.

Consider this command:

```

```

A successful command indicates that the API operation succeeded. It does not mean that the scheduler has completed its decision or that the application is ready to serve requests.

Useful commands for observing each stage are:

```
kubectl get pods -o wide
kubectl describe pod <pod-name>
kubectl get events --sort-by=.metadata.creationTimestamp

```

Use the appropriate namespace with `-n <namespace>` when the Pod is not in the default namespace.

## 4. Scheduling decisions: filtering and scoring

A useful way to understand the scheduler is to separate its decision into two conceptual stages: filtering and scoring.

The exact internal implementation is plugin-based, and the set of plugins and their configuration can vary. Filtering and scoring remain useful concepts for understanding the scheduling process.

### 4.1 Filtering: which nodes are eligible?

Filtering evaluates whether a node can satisfy the Pod's scheduling requirements.

Suppose a Pod requests 2 CPU cores and 4 GiB of memory. The cluster contains four nodes:

| Node   | Available schedulable CPU | Available schedulable memory | Other condition          |
| ------ | ------------------------- | ---------------------------- | ------------------------ |
| Node A | 1 CPU                     | 8 GiB                        | Insufficient CPU         |
| Node B | 4 CPU                     | 8 GiB                        | Meets requirements       |
| Node C | 4 CPU                     | 2 GiB                        | Insufficient memory      |
| Node D | 8 CPU                     | 16 GiB                       | Has an untolerated taint |

For this example, assume the Pod has no toleration for Node D's taint and that the listed resources represent capacity available for scheduling after existing requests.

### Filtering result

Node A

Rejected: insufficient CPU capacity

Node B

Feasible: resource and scheduling requirements are satisfied

Node C

Rejected: insufficient memory capacity

Node D

Rejected: the Pod does not tolerate the node's taint

The scheduler cannot simply select Node D because it has more free resources. An untolerated `NoSchedule` taint makes it ineligible for this Pod.

If all nodes fail filtering, the Pod remains unscheduled. Kubernetes reports scheduling events explaining the relevant failures where possible.

### 4.2 Scoring: which feasible node is preferable?

If several nodes pass filtering, the scheduler can score them according to configured scheduling plugins.

Possible considerations include:

- Resource distribution and resource utilization.
- Node affinity preferences.
- Pod affinity and anti-affinity preferences.
- Topology distribution preferences.
- Other enabled scoring plugins.

A simplified scoring model is:

\\[ S(n)=\sum\_{i=1}^{k} w_i\\,s_i(n) \\]

Where:

- \\(S(n)\\) is the combined score for node \\(n\\).
- \\(s_i(n)\\) is the score assigned by plugin \\(i\\).
- \\(w_i\\) is the configured weight of that plugin.
- \\(k\\) is the number of scoring plugins contributing to the result.

This is a conceptual model rather than a promise that every scheduling decision uses one identical formula. Actual plugin scores, normalization, weights, and scheduling profiles depend on the scheduler configuration.

The highest-scoring node is generally preferred among the feasible candidates. However, a high score does not override a hard scheduling constraint.

Important distinction: Filtering determines where a Pod is allowed to run. Scoring helps determine which allowed node is preferred.

## 5. CPU, memory, requests, limits, and allocatable capacity

Resource accounting is one of the most important scheduling concepts. Many scheduling failures occur because engineers confuse actual resource usage with the resources Kubernetes considers when placing a Pod.

### 5.1 Resource requests

A resource request specifies the amount of a resource that Kubernetes uses for scheduling and resource allocation decisions.

Example:

```
apiVersion: v1
kind: Pod
metadata:
  name: api-example
spec:
  containers:
    - name: api
      image: nginx:1.28
      resources:
        requests:
          cpu: "500m"
          memory: "512Mi"
```

Here:

- `cpu: "500m"` means 500 millicores, or half of one CPU core.
- `memory: "512Mi"` means 512 mebibytes of memory.

A CPU request of `1000m` is equivalent to one CPU core. A request of `250m` is equivalent to one-quarter of a CPU core.

Requests are especially important because the scheduler uses them to assess whether a node can accommodate the Pod.

### 5.2 Resource limits

A resource limit defines a configured upper bound on a container's resource consumption, enforced through the relevant Kubernetes and operating-system mechanisms.

For CPU, exceeding the configured limit generally causes throttling rather than immediate container termination. For memory, exceeding the limit can result in the container being terminated by an out-of-memory mechanism.

Consider:

```
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"
```

This means the container requests half a CPU core and 512 MiB of memory, while its configured limits are one CPU core and 1 GiB of memory.

A limit is not a reservation that the scheduler subtracts from the node's allocatable capacity in the same way as a request. For ordinary container resource scheduling, requests are the key quantities used to evaluate placement.

### 5.3 Why actual usage and scheduling capacity differ

Suppose a node has 8 CPU cores. Existing Pods request a total of 6 CPU cores, but their current measured CPU usage is only 2 cores.

A new Pod requests 3 CPU cores.

The scheduler generally cannot treat the 4 apparently idle cores as fully available merely because current CPU usage is low. The node has only 2 CPU cores of unrequested capacity under this simplified example.

\\[ 8 - 6 = 2 \text{ CPU cores available for additional requests} \\]

The new Pod's 3-core request does not fit, even though instantaneous CPU usage is low.

This behavior protects workloads against oversubscription of their requested capacity. It also means that inefficiently large requests can prevent Pods from being scheduled despite seemingly idle hardware.

### 5.4 Node capacity versus node allocatable

These two node properties are related but not identical.

- Capacity represents the node's total reported resource capacity.
- Allocatable represents the resources available for Pods after accounting for resources reserved for system needs and other applicable reservations.

For example, a worker node might report:

```
Capacity:
  cpu:     8
  memory:  32Gi

Allocatable:
  cpu:     7500m
  memory:  29Gi
```

The difference may account for operating-system processes, Kubernetes system components, and configured reservations. The actual values depend on the node configuration and environment.

The scheduler uses allocatable resources and accounts for existing scheduled workloads' requests when assessing fit.

To inspect resource information:

```
kubectl describe node <node-name>
```

Look for the `Capacity`, `Allocatable`, and `Allocated resources` sections.

### 5.5 How requests are accounted for across containers

For ordinary non-init application containers, a Pod's CPU and memory requests are generally calculated by adding the requests of its containers.

For example:

```
spec:
  containers:
    - name: api
      image: nginx:1.28
      resources:
        requests:
          cpu: "500m"
          memory: "512Mi"

    - name: proxy
      image: nginx:1.28
      resources:
        requests:
          cpu: "250m"
          memory: "256Mi"
```

Ignoring other resource-accounting complications, this Pod requests:

- CPU: `750m`
- Memory: `768Mi`

Real-world calculations can be more involved because init containers, restartable sidecar init containers, Pod overhead, extended resources, and Pod-level resource features where enabled can affect accounting.

Do not assume every Pod's effective resource request is always a simple sum of every container field in the YAML.

## 6. Node selection and node affinity

Kubernetes supports several mechanisms for controlling where Pods can run. These mechanisms differ in how strict they are and whether they describe node properties or relationships between workloads.

### 6.1 Node labels

Node labels are key-value pairs attached to Node API objects. They provide attributes that Pods can reference when expressing placement requirements.

For example, a node might have labels such as:

```
kubernetes.io/arch=amd64
kubernetes.io/os=linux
nodepool=general
workload=compute
```

An administrator can inspect and manage labels with commands such as:

```
kubectl get nodes --show-labels

kubectl label node <node-name> workload=compute
```

Labels alone do not cause a workload to run on a node. A Pod must express an appropriate selection or affinity rule, or another scheduling mechanism must influence placement.

### 6.2 `nodeSelector`: the simplest hard constraint

A `nodeSelector` requires the Pod to run on a node containing all specified label key-value pairs.

```
apiVersion: v1
kind: Pod
metadata:
  name: compute-pod
spec:
  nodeSelector:
    workload: compute
    kubernetes.io/os: linux
  containers:
    - name: app
      image: nginx:1.28
```

This Pod can be scheduled only on nodes whose labels satisfy both requirements.

If no suitable node exists, the Pod remains unscheduled. Kubernetes does not silently ignore the selector to make progress.

Use `nodeSelector` when simple equality-based node selection is sufficient.

### 6.3 Node affinity

Node affinity provides a more expressive way to constrain or prefer node placement.

There are two important categories:

- `requiredDuringSchedulingIgnoredDuringExecution`
- `preferredDuringSchedulingIgnoredDuringExecution`

The first expresses a hard scheduling requirement. The second expresses a preference that contributes to node scoring.

Example of a hard requirement:

```
apiVersion: v1
kind: Pod
metadata:
  name: compute-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: workload
                operator: In
                values:
                  - compute
                  - analytics
  containers:
    - name: app
      image: nginx:1.28
```

The Pod requires a node whose `workload` label is either `compute` or `analytics`.

Common label selector operators include:

- `In`: the label value must match one of the supplied values.
- `NotIn`: the label value must not match any supplied value.
- `Exists`: the label key must exist.
- `DoesNotExist`: the label key must not exist.
- `Gt` and `Lt`: compare numeric label values under the applicable selector rules.

Multiple expressions within a single `nodeSelectorTerm` must all match. Multiple terms in the `nodeSelectorTerms` list are alternatives: matching any term is sufficient.

### 6.4 Preferred node affinity

A preference does not necessarily prevent scheduling on other nodes.

```
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
            - key: workload
              operator: In
              values:
                - compute
```

This expresses a preference for nodes labeled `workload=compute`. The weight contributes to preference scoring; it is not a guarantee that the Pod will be scheduled there.

If every node with that label is unavailable or fails a hard requirement, the scheduler can select another feasible node.

### 6.5 What does `IgnoredDuringExecution` mean?

The suffix describes what happens if a node's labels change after the Pod has already been scheduled.

For these node-affinity rules, Kubernetes uses the rule during scheduling but does not automatically evict the already-running Pod merely because a later label change makes the rule no longer match.

This is an important operational distinction. A scheduling rule is not necessarily a continuous enforcement mechanism after placement.

## 7. Pod affinity and Pod anti-affinity

Node affinity concerns the properties of nodes. Pod affinity and anti-affinity concern the placement of Pods relative to other Pods.

These rules are often used to co-locate related services or distribute replicas across failure domains.

### 7.1 Pod affinity

Pod affinity expresses a preference or requirement for placement in a topology containing matching Pods.

For example, an application might benefit from running in the same availability zone as a related service. A Pod-affinity rule can express a relationship to existing Pods selected by labels.

The basic structure looks like this:

```
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: cache
        topologyKey: topology.kubernetes.io/zone
```

This fragment is illustrative and would need to be included in a complete Pod specification. It requires the scheduler to place the Pod in a qualifying topology domain associated with matching `app=cache` Pods.

The `topologyKey` determines the node label used to define that domain. With `topology.kubernetes.io/zone`, the relevant domain is an availability zone.

Pod affinity can help with locality, but it can also create restrictive dependencies. If the required matching Pods do not exist in a suitable topology domain, the new Pod might remain unscheduled.

### 7.2 Pod anti-affinity

Pod anti-affinity expresses a preference or requirement against placing a Pod in a topology domain containing matching Pods.

A common example is spreading replicas of the same application across nodes:

```
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: payments-api
          topologyKey: kubernetes.io/hostname
```

This rule prefers nodes that do not share the specified hostname topology domain with matching Pods.

If two nodes have different `kubernetes.io/hostname` values, they represent different node-level topology domains for this rule.

### 7.3 Required versus preferred anti-affinity

A hard anti-affinity rule can prevent two matching Pods from being placed in the same topology domain. This may improve isolation but reduce scheduling flexibility.

For example, suppose an application has five replicas and the cluster has only three eligible nodes. If a required anti-affinity rule prohibits two replicas from sharing a node, at most three replicas can be scheduled.

The remaining two Pods may remain Pending until additional eligible nodes become available or the constraints change.

A preferred anti-affinity rule instead asks the scheduler to avoid co-location where practical. It can still allow co-location when hard requirements and cluster capacity make that the best feasible outcome.

Design principle: Use hard placement constraints when they are necessary for correctness or isolation. Prefer soft constraints when availability and flexibility are more important than enforcing an absolute placement rule.

## 8. Taints and tolerations: controlling which workloads may use a node

Node affinity and `nodeSelector` allow a Pod to request certain nodes. Taints provide a complementary mechanism: they allow a node to repel Pods that do not explicitly tolerate the taint.

This distinction is critical in clusters where some nodes are reserved for specialized workloads.

### 8.1 Taints

A taint is applied to a node and consists of a key, an optional value, and an effect.

For example:

```
kubectl taint nodes <node-name> workload=critical:NoSchedule
```

This adds a taint with:

- Key: `workload`
- Value: `critical`
- Effect: `NoSchedule`

A Pod that does not tolerate this taint will not ordinarily be scheduled onto that node.

Taints are commonly used to reserve nodes for particular workloads, isolate specialized hardware, or keep ordinary application workloads away from control-plane or dedicated infrastructure nodes.

### 8.2 Taint effects

Kubernetes supports three principal taint effects.

| Effect             | Scheduling and execution behavior                                                                                                                          |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NoSchedule`       | New Pods that do not tolerate the taint are not scheduled onto the node. Existing Pods are not automatically evicted just because this taint is added.     |
| `PreferNoSchedule` | The scheduler attempts to avoid placing non-tolerating Pods on the node, but this is a preference rather than a hard prohibition.                          |
| `NoExecute`        | Non-tolerating Pods are evicted from the node, subject to applicable toleration behavior. New non-tolerating Pods are also prevented from remaining there. |

For `NoExecute`, a toleration can include `tolerationSeconds`, which specifies how long a Pod may remain after the relevant taint is present before eviction. The precise behavior depends on the taint and toleration matching rules.

### 8.3 Tolerations

A toleration tells Kubernetes that a Pod is permitted to tolerate a matching taint. It does not guarantee that the Pod will be scheduled onto the tainted node.

Example:

```
apiVersion: v1
kind: Pod
metadata:
  name: critical-api
spec:
  tolerations:
    - key: workload
      operator: Equal
      value: critical
      effect: NoSchedule
  containers:
    - name: api
      image: nginx:1.28
```

This Pod tolerates the example `workload=critical:NoSchedule` taint.

However, if the node lacks sufficient resources, fails the Pod's node affinity, or violates another hard scheduling constraint, the Pod still cannot be scheduled there.

### 8.4 Taints do not automatically select workloads

Consider a node with the taint:

```
workload=critical:NoSchedule
```

There are two independent questions:

1. Is a Pod allowed to run on this node?
2. Does the Pod actually prefer or require this node?

A toleration addresses the first question. Node affinity or a selector can address the second.

If a Pod tolerates the taint but has no selection rule, it may be scheduled onto another eligible node instead.

For dedicated workload pools, combining a taint with matching node affinity is often useful:

- The taint keeps ordinary workloads away.
- The affinity rule directs the intended workload toward the dedicated nodes.

This combination is stronger than using either mechanism alone.

## 9. Topology spread constraints: distributing replicas across failure domains

Running several replicas does not automatically guarantee that Kubernetes distributes them evenly across nodes or availability zones.

A Deployment with six replicas could, under suitable conditions and absent relevant placement constraints, place several replicas on the same node. If that node fails, the workload could lose a large proportion of its capacity.

Topology spread constraints let you specify how matching Pods should be distributed across topology domains.

### 9.1 Understanding topology domains

A topology domain is a grouping of nodes based on a shared node label.

Common examples include:

- `kubernetes.io/hostname`: individual nodes.
- `topology.kubernetes.io/zone`: availability zones.
- `topology.kubernetes.io/region`: regions.

Suppose a cluster has six eligible nodes distributed across three availability zones.

### Example: six replicas across three zones

Zone A

2 replicas

Zone B

2 replicas

Zone C

2 replicas

Illustrative balanced placement. Actual distribution depends on the configured constraints, eligible domains, capacity, and other scheduling rules.

If one availability zone becomes unavailable, the remaining zones may still host replicas and serve traffic, provided sufficient capacity and application-level resilience exist.

### 9.2 Example topology spread configuration

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 6
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: payments-api
      containers:
        - name: api
          image: nginx:1.28
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
```

The important fields are:

- `maxSkew`: the maximum permitted difference in matching Pod counts between relevant topology domains under the constraint's counting rules.
- `topologyKey`: the node label defining the domains.
- `whenUnsatisfiable`: determines what happens when the constraint cannot be met.
- `labelSelector`: identifies the Pods counted for this distribution rule.

With `DoNotSchedule`, the scheduler leaves a Pod unscheduled if placing it would violate the constraint. With `ScheduleAnyway`, the scheduler treats the distribution goal as a scoring preference instead.

The example omits `minDomains`, `nodeAffinityPolicy`, and `nodeTaintsPolicy`, whose defaults and availability depend on the Kubernetes version. Those options can matter when some domains are missing or nodes are ineligible.

### 9.3 Topology spread versus Pod anti-affinity

These mechanisms solve related but different problems.

Pod anti-affinity can express that matching Pods must not share a topology domain, or should preferably avoid doing so.

Topology spread constraints express a desired balance of matching Pods across multiple domains.

For example, hard anti-affinity at the node level can enforce at most one matching replica per node. Topology spread can instead permit multiple replicas per node while trying to balance counts across zones or nodes.

For many replicated services, topology spread is a more flexible tool for controlling distribution. It still needs to be designed alongside resource capacity, autoscaling, and application availability requirements.

## 10. Pod priority and preemption

Sometimes a cluster has insufficient free resources to schedule every Pod immediately. Kubernetes provides priority mechanisms so that higher-priority workloads can be scheduled ahead of lower-priority workloads.

### 10.1 Priority classes

A `PriorityClass` assigns a numerical priority to Pods that reference it. Higher values indicate higher priority.

Example:

```
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: production-critical
value: 100000
globalDefault: false
description: "Priority for critical production workloads"
```

A Pod can then reference it:

```
apiVersion: v1
kind: Pod
metadata:
  name: critical-api
spec:
  priorityClassName: production-critical
  containers:
    - name: api
      image: nginx:1.28
      resources:
        requests:
          cpu: "2"
          memory: "2Gi"
```

Priority affects scheduling order and can influence preemption. It does not create CPU, memory, or additional nodes.

The priority class itself must exist, and the requesting user must have the required permissions and comply with cluster policy.

### 10.2 What is preemption?

Preemption is a mechanism by which the scheduler may remove lower-priority Pods from a node to make room for a higher-priority Pod that cannot otherwise be scheduled.

A simplified example:

- Node A has capacity for 8 CPU cores.
- Existing Pods have requests totaling 7 CPU cores.
- A high-priority Pod requests 3 CPU cores.
- The node has only 1 CPU core of unrequested capacity.

If removing a suitable lower-priority Pod would allow the high-priority Pod to fit, preemption may make that placement possible.

However, preemption is not guaranteed. The scheduler must find a suitable candidate node and a set of lower-priority victims whose removal makes the Pod feasible. Other constraints, including affinity and disruption considerations, can affect the outcome.

### 10.3 Priority is not the same as readiness or importance to users

A high-priority Pod may be scheduled before a lower-priority Pod, but that does not make it automatically healthy or available.

Priority also does not guarantee that the cluster has enough capacity to run all workloads. If no feasible placement can be achieved, even a high-priority Pod may remain Pending.

Production principle: Use priority classes deliberately. Overusing high priorities can undermine the isolation and scheduling guarantees that lower-priority workloads rely on.

## 11. Why Pods remain Pending: a systematic troubleshooting method

The `Pending` phase is one of the most misunderstood states in Kubernetes. It does not always mean that the scheduler has failed.

A Pod can remain Pending because it has not been assigned to a node, or because it has been assigned but is still waiting for required setup work, such as volume attachment or image-related preparation.

Therefore, always distinguish an unscheduled Pod from a scheduled Pod that has not started successfully.

### 11.1 Start with the Pod's node assignment

Run:

```
kubectl get pods -o wide
```

Check the `STATUS` and `NODE` columns.

- If `NODE` is empty, the Pod may not have been scheduled.
- If `NODE` contains a node name, the scheduler has assigned it, but startup may still be in progress or blocked.

Next, inspect the detailed events:

```
kubectl describe pod <pod-name> -n <namespace>
```

The `Events` section often provides the most direct explanation.

### 11.2 Common causes of scheduling failure

| Symptom or event                            | Likely cause                                                | What to investigate                                          |
| ------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------ |
| `Insufficient cpu`                          | Requested CPU does not fit                                  | Node allocatable capacity and existing requests              |
| `Insufficient memory`                       | Requested memory does not fit                               | Pod memory requests and node capacity                        |
| `didn't match Pod's node affinity/selector` | No node matches required labels                             | `nodeSelector`, node affinity, node labels                   |
| `untolerated taint`                         | Pod does not tolerate a node taint                          | Node taints and Pod tolerations                              |
| `Too many pods`                             | Node reached its applicable Pod-count limit                 | Node Pod capacity and networking configuration               |
| Topology constraint violation               | Placement would violate required distribution               | Topology domains, matching Pods, available nodes             |
| PVC-related scheduling event                | Volume topology or storage requirements cannot be satisfied | PVC/PV state, storage class and zone compatibility           |
| No nodes available                          | All candidates are ineligible or unavailable                | Node readiness, cordoning, resource requests and constraints |

These messages are examples; exact event wording and details vary by Kubernetes version and scheduling plugins.

Useful commands include:

```
kubectl get nodes
kubectl describe node <node-name>
kubectl get pods -A -o wide
```

Look for:

- Nodes that are `NotReady`.
- Nodes marked unschedulable.
- High existing CPU or memory requests.
- Resource reservations that reduce allocatable capacity.
- Taints and labels that exclude the Pod.
- Other Pods already occupying the eligible nodes.

Remember that `kubectl top nodes` shows observed resource usage, provided Metrics Server or a compatible metrics provider is available. It does not replace inspection of scheduling requests and allocatable resources.

### 11.5 What if the Pod is scheduled but still Pending?

If the `NODE` column is populated, investigate the startup path instead of assuming that scheduling is the problem.

```
kubectl describe pod <pod-name> -n <namespace>
kubectl get pod <pod-name> -n <namespace> -o yaml
```

Potential causes include:

- Container image pull failures.
- Volume mount or attachment delays.
- CNI or networking setup problems.
- Init containers that have not completed.
- Container runtime problems on the node.

A Pod's lifecycle phase, its container states, and its readiness conditions describe different aspects of progress. Use all of them when diagnosing a problem.

## 12. Kubernetes scheduling in AWS EKS

The same scheduling principles apply to Amazon EKS because EKS runs Kubernetes. However, EKS adds infrastructure-specific considerations that make capacity planning and troubleshooting particularly important.

### 12.1 The scheduler does not automatically create nodes

Suppose a Deployment requests 20 replicas, but the cluster has capacity to accommodate only 12 replicas according to their resource requests.

The scheduler can place the 12 replicas that fit. The remaining Pods may stay Pending.

The scheduler does not independently provision additional EC2 instances simply because Pods cannot fit.

Node provisioning requires a separate mechanism, such as an appropriately configured EKS managed node group with Cluster Autoscaler or a compatible provisioning controller such as Karpenter.

Deployment requests 20 replicas

Scheduler places 12 replicas

Remaining 8 Pods cannot fit on eligible nodes

Node autoscaling mechanism

Evaluates whether additional node capacity can resolve the unschedulable Pods

New node capacity becomes available

The scheduler can retry and place eligible Pending Pods

Autoscaling is not guaranteed to resolve every scheduling failure. A Pod may remain unschedulable because of an impossible affinity rule, an incompatible architecture, unavailable instance types, exhausted cloud quotas, subnet IP shortages, or other infrastructure constraints.

### 12.2 Availability zones and storage

An EKS cluster can span multiple availability zones, but workloads do not automatically distribute themselves optimally across those zones.

You must consider:

- Node group distribution across availability zones.
- Topology spread constraints and Pod anti-affinity.
- Persistent volume topology and availability zone compatibility.
- Available IP addresses in the relevant subnets.
- Capacity in the node instance types and node groups.

A Pod requiring a volume bound to a particular availability zone may not be schedulable on a node in a different zone, even if that node has sufficient CPU and memory.

### 12.3 Practical EKS debugging checklist

When a Pod is Pending in EKS, check the Kubernetes-level issue first:

```
kubectl describe pod <pod-name> -n <namespace>
kubectl get nodes -L topology.kubernetes.io/zone
kubectl describe node <node-name>
kubectl get pvc -n <namespace>
```

If the events suggest that additional node capacity is required, investigate the configured autoscaler, node group limits, EC2 capacity availability, subnet IP capacity, and AWS service quotas.

Do not assume that every Pending Pod is an EKS infrastructure issue. Many are caused by requests or placement constraints in the workload manifest.

### Step 2: Inspect resource requests

```
kubectl get pods -n k8s-scheduling-lab -o yaml
kubectl describe node <node-name>
```

Inspect the Pod specifications and node resource allocation. Note that the initial Deployment may not specify explicit requests, so admission policies or configured defaults can affect the effective resource requirements.

### Step 3: Inspect node labels

```
kubectl get nodes --show-labels
```

Choose a label that actually exists on an eligible node. Do not assume that a custom label is present.

### Step 4: Add a hard node selector

For a controlled experiment, edit the Deployment:

```
kubectl edit deployment web -n k8s-scheduling-lab
```

Under `spec.template.spec`, add a `nodeSelector` that references a label and value you have verified on at least one eligible node.

For example, if your cluster has nodes labeled `workload=compute`:

```
spec:
  template:
    spec:
      nodeSelector:
        workload: compute
```

Save the change and observe the rollout:

```
kubectl rollout status deployment/web -n k8s-scheduling-lab
kubectl get pods -n k8s-scheduling-lab -o wide
kubectl describe pods -n k8s-scheduling-lab
```

If no eligible node has the required label, replacement Pods may remain Pending. That is expected: the scheduler must respect the hard requirement.

After collecting your observations:

```
kubectl delete namespace k8s-scheduling-lab
```

Caution: Delete the namespace only if you created it specifically for this lab and have confirmed that it contains no resources you need to retain.

## 14. Common misconceptions to avoid

1. “The scheduler chooses the node with the most free CPU.” Not necessarily. A node must first satisfy all relevant hard constraints, and the scheduler then considers configured scoring rules.
2. “Resource limits determine whether a Pod fits on a node.” For ordinary container scheduling, resource requests are the primary inputs to resource-fit decisions. Limits serve a different purpose.
3. “A toleration forces a Pod onto a node.” A toleration permits the Pod to tolerate a matching taint. It does not select that node or override other scheduling requirements.
4. “A scheduled Pod is a running Pod.” Scheduling assigns a node. The kubelet and other node components must still prepare and start the workload.
5. “A Deployment with multiple replicas automatically spreads them across zones.” Not necessarily. Use topology spread constraints or other suitable placement rules when distribution is a requirement.
6. “The scheduler adds EC2 instances when the cluster runs out of capacity.” Node provisioning is the responsibility of a separate infrastructure or autoscaling mechanism.
7. “Pending always means a scheduling failure.” Not always. A Pod can be assigned to a node and still be waiting for startup operations.
